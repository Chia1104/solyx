# `@solyx/agent`

The trading agent on pi (`@earendil-works/pi-durable` and `pi-ai`): its runtime, tools, prompt and skills, and the wire events a renderer folds into a conversation.

## Boundaries

- Everything but `./wire`, `./providers`, `./skill-source` and `./mcp-config` runs only in the main process: it holds API keys and calls providers. Those four import nothing from pi or Node, so the renderer uses them for the event union, tool names, the fold, what a message names, the provider and thinking choices, skill sources and the MCP file.
- Tools read through `TradingToolPorts`, whose desk is a `ProposingDesk`: they may propose, check and read the account, never `confirm`; see the trading invariants. `get_calendar` reads the host's calendar through the same port the overview shows, so the agent's dates and the app's are one list, and the prompt has the agent read it before searching the web for dates. Tools are installed once rather than built per run, so `propose_order`'s one proposal per run is claimed in the conversation's durable state.
- The providers are pi-ai's built-in ones that run on a single key, by pi-ai's id: `createModelCatalog` withholds the rest (cloud credentials on this computer, more fields than a key, a sign-in the app does not keep), and a test fails when a provider it offers asks for more than one key or, signing in alone, for any. A provider with a subscription also signs in, and the catalog names which: it keeps pi-ai's own sign-in only for those, xAI's, Meta's and GitHub Copilot's, whose flows run on a code the user enters on the provider's page, open no listener and read nothing from the environment, and strips every other. pi-ai's flows are all registered with it up front, since a bundled main process cannot load one by its file and pi-ai registers no fewer, so every flow's module is loaded but only a kept provider's can run; a built app, not a test, is what shows a flow loads. GitHub Copilot runs on its sign-in alone, so the catalog strips its key instead, signs in to github.com only, and lists for it the models its account has, which the sign-in carries: a default or a pick the account lacks reads as the first model it has. `./providers` holds only the id's shape, so the renderer learns the providers from the host, and each provider's default model stays behind the catalog.
- `createModelCatalog` owns every call into pi-ai's model catalog and gives pi-ai an auth context with no environment or files, so keys come only from the settings the user saved: pi-ai resolves every request's credential in the host's `ProviderCredentials`, the saved API key or the subscription sign-in, which the catalog refreshes. Where all of a provider's models share one endpoint, they are served from the one the host names, read for every request. OpenAI signs in through `./chatgpt-oauth`, the app's own Sign in with ChatGPT flow, in place of pi-ai's, so OpenAI's consent screen names Solyx. OpenRouter signs in through `./openrouter-key`, the app's own run of OpenRouter's flow for apps, which ends in a key the user owns; the host saves it as the provider's API key, so OpenRouter never runs on a sign-in. Both wait for the browser on `./sign-in-callback`'s listener, bound to `127.0.0.1` and open only while its sign-in waits, and the browser lands on the host's page. A sign-in by code hands the host its code to show, and the catalog opens only an https page a flow names.
- A conversation a scheduled task started keeps that task's id and name in a doc of its own, which only the host can set as it makes the conversation, so a renderer's setup never claims one. Its messages carry a `scheduled` line in their context, and a `changed` line for each thing the app saw change where that is why the task runs, and the prompt has the agent work without asking, leave calls that must ask for last and end with what the user should read. The approval gate is the same as in any conversation: a call that must ask waits for the user.
- A conversation runs on its own model and thinking level where the user picked them, kept with the conversation, and otherwise on the host's default. The host resolves the pick before every run and refuses one it cannot run, such as a model of a provider the user switched off, rather than run another model in its place.
- Conversations run on pi-durable's Harness over the store `@solyx/db/agent` opens. pi-durable stores every message, the reply streaming and each tool call before anything is shown, and the runtime sends wire events from what it stored. The system prompt is sections rendered before every request, and only a section that changed is stored and sent again. A storage error ends the Harness for the life of the process: the runtime ends the runs under way as `store-failed`, tells the host once, and every call after it fails. Nothing is retried or reopened in place, since the runs carry on from what was stored when the app next starts.
- The runtime sends what the next request holds as pi-ai estimates it from the stored context, before the events of each commit that changes it, so a run's end stays its last event. A reply carries its own count. pi-durable compacts a conversation as it fills, and `compact` does so when the user asks, on the model the next run would use, and is refused while a run or another such compaction goes; stopping the conversation stops it. A summary shows where it was placed, and the messages before it stay in the thread.
- The app's per-turn context (the time on each exchange and on the user's own clock, the session the host says each market is in, account mode, what the user has on screen (a listing with its chart's interval and what is drawn on it, or the page of the overview or of the settings), the listings the user named with `@` and the skill a leading `/name` asked for, the reply language) rides in the user message as an `<app_context>` block rather than in the system prompt, so the prompt stays cacheable and a replayed transcript sends the same bytes. `userText` strips it for display.
- The prompt tells the agent where the host's pages are, a listing's and the overview's, so a reply can link them. The host hands those addresses in as `PromptSources.links`, built from its own router's shapes, and the package writes no route of its own.
- A run the app's exit cut off continues once `resume` runs at the next start. A tool call it cut off runs again only when its tool is declared `replay: "safe"`; otherwise the model is told the call was interrupted. Only tools that change nothing are safe, plus `propose_order` and `submit_forecast`, whose calls keep the id of what they make in a durable memo so the desk returns what was already made under it, `remember` and `forget`, whose calls change the same memory again, `change_setting`, which saves the same value again, `save_theme` and `save_task`, whose calls keep the id of what they write, `change_watchlist`, which leaves a listing already as asked alone, an MCP tool its user lets run without asking, and `codemode`, whose script carries on from the results it already got, so a call it finished is never sent twice and one it was cut off in follows its own tool's rule.
- Skills come from three places, and a name taken by an earlier one hides later ones: the user's own `skills/` in the config folder, the built-ins in `skills.ts`, then `~/.agents/skills`, whose skills are offered only once the user switches them on. `loadSkillCatalog` reads each folder's `<name>/SKILL.md`, and the prompt's skills section and `read_skill` read the catalog for every request. The user may ask for a skill by starting a message with `/name`, unless its frontmatter sets `user-invocable: false` as other agents read it: that marks background the agent reads on its own, as the built-in market rules and canvas are. A name `AgentCommand` holds, such as `compact`, is the app's own and never reaches the agent, so no skill of that name can be asked for. `./wire`'s `messageParts` is the one grammar for what a message names: the host resolves what it finds, and the renderer marks it. Files can add playbooks, standing instructions (`AGENTS.md`) and scripts the shell may run, never tools: the tools stay in code, so `propose` remains the agent's only road to an order.
- A reply draws figures as a canvas, an `html` fence the host draws in a frame that runs no script. The prompt has the agent draw what a reader would line up, and the `canvas` skill has it give each figure as its tool gave it and leave the figure's place to the marks the host's stylesheet draws by class, so that playbook and the host's stylesheet change together.
- `./shell` is pi-durable's `bash` on the user's computer (PowerShell on Windows), with no sandbox, and the only way a skill's scripts run. It exists only while the host puts it in the toolset. Every command goes through the approval gate, and only its conversation's approval mode lets one run unasked: in `auto`, the host's decisions model judges the command, and it runs when every risk it scores is unlikely; a command starts in its conversation's own folder with the environment `./process-env` gives a stdio MCP server, never the app's. A command the user allows can still reach anything their account can, including the app's files, so the host offers the shell only beside a paper account, and `read_skill` names a skill's folder only while the shell is offered.
- `./mcp` connects the servers in `mcp.json` through pi-mcp.
  - Their tools wait until the agent loads them: every request offers the app's own tools and pi-durable's `tool_search`, which loads the MCP tools it finds into the conversation. It matches English words only, so the prompt has the agent search in English. Until then only each server's name, tool count and description reach the model, the one the user wrote in `mcp.json` or else the name the server gives itself, never its instructions.
  - A stdio server starts with the user's home, name and shell, the login shell's `PATH` and what its entry names, never the rest of the app's environment.
  - Each tool runs under the user's policy: off, ask (each call goes through the approval gate) or auto, which holds only for tools their server marks read-only. A tool that asks is guarded itself, so the agent's calls and a script's ask alike.
  - MCP tools can reach anything outside the app, so the prompt treats every tool's output as data, never instructions.
  - A remote server that answers 401 waits for the user to sign in through pi-mcp's OAuth flow, the host's browser and a loopback callback, and the host keeps the grant. Only a sign-in the user starts opens the browser. Model and MCP sign-ins alike run one at a time: a new one cancels the one still open.
- `./script-runner` runs the agent's own JavaScript in a QuickJS VM (pi-codemode), each script on a worker thread of its own with a memory limit; a script reaches only the functions its tool hands it, and the runner stops those still running as the app quits. It also holds the one sandbox `codemode` runs its scripts in.
- `./mcp-script` is `codemode`, pi-durable's code mode: a script whose only reach is the MCP tools the policies offer, each a nested tool call, which it finds with `searchTools`, `describeTool` and `describeNamespace`, a server being a namespace, so the tool's description never names one and servers connecting do not change it. Each call runs under its tool's policy as a direct call would: an asking one goes through the approval gate as `<script call id>/c<n>`, and a refused one throws in the script. A script waits on the user, so it has no deadline unless it sets one; stopping its run stops it, and one the app's exit cut off carries on at the next start, where a call left waiting is not sent and fails in the script. A script gets no models and no environment, so what it prints is never written to a file. A running script's calls show as they happen; a transcript read from storage shows them as the script's result lists them, arguments cut short when long, and none for a script stopped before it ended.
- `./analysis` is `run_analysis`: a script with a deadline. It can call only the functions `createAnalysis` gives it, which read market data and the account and compute the app's indicators, and those of `./analysis-sources`, which read quotes, sectors, flows and filings through the host's own readers, each source under a name of its own (`market`, `flows`, `fundamentals`) with the figures the app computes from it; it has no network, files, timers or modules, and no function it can call changes anything. A source that counts requests is read for at most `MAX_LISTINGS` listings a script, since its limit is the whole app's, and a function that reads one dataset costs only that dataset's requests, so a source is split by dataset rather than served whole. A script may ask for daily or longer bars from further back than the app's own history, up to ten years and for a few listings a script, since each year costs the source a request the first time; those bars are prices as traded, so `fundamentals.cashGoneEx` gives the cash to add back as a forecast's judging does. Every function's types ride in the tool's description, declared once by name; past a few thousand tokens of them the sources should move behind a catalog a script asks, as MCP tools are. That is why its calls need no approval: a function that proposes, calls an MCP tool or reaches outside the app never joins that list, and MCP tools are `./mcp-script`'s alone. What a script stores for the conversation's later scripts is kept in the conversation.
- `./web` searches and reads the web through the vendor the host hands it (`WebSearch` and `WebReader` from `@solyx/core/web-search`), and exists only while the host puts it in the toolset, which it does while the user's vendor has a key. A search changes nothing and goes only to that vendor, so it runs unasked. Reading a page fetches an address the model wrote, which could carry what the conversation holds to a host a page named, so every read goes through the approval gate; in `auto` one runs unasked only at an address the conversation's own `web_search`, `get_news` or `search_history` showed the model, which those tools note in the conversation's durable state.
- `./memory` is what the agent keeps across conversations, in the host's `MemoryStore` from `@solyx/core/memory`. The prompt lists each memory's description, up to a fixed length, and `recall` reads and searches them all. Both writes go through the approval gate, their arguments checked before the user is asked, so a call that cannot run never asks. `remember` is guarded with a check that always passes, so it waits for the user only in a conversation set to `ask` and the agent keeps learning them in one set to `auto`, a scheduled run among them: a memory changes only what the agent keeps, and the user reads and edits every one. `forget` has no check, since forgetting cannot be undone, so only `bypass` lets it run unasked. The prompt has the agent save what it learns of the user on its own, from what they say and what they do with proposals and their account, never from what pages or tools said, and say in its reply what it saved. Where the host gives a model on this computer, a new memory that reads as one of its kind and listing already kept, above the line `MEMORY_LINES` holds for the space, is refused with that memory's id unless the call says it is distinct. The prompt treats a memory as what was true when it was written, never as instructions or current data. Scripts never reach memories.
- `./research` reads and writes a listing's research through the host's `ResearchDesk` from `@solyx/core/research` (`get_research`, `revise_report`, `submit_forecast`) and reads its filed figures with `get_fundamentals`, which the app computes, so the model cites them rather than working them out. Its answer names the source and tells apart a market no source covers, a part the source has none of on file and a part that could not be read, so a figure that is missing is never taken for a listing that files none, and it opens with what a fund is where its exchange lists it as one, and with the multiples its exchange works out, which it words as the exchange's beside the app's own, and where each stands in the listing's industry. `get_research` also says how each stretch of the report's stance has done against the market's index, so a view over quarters is answered for like a forecast over sessions. `get_base_rates` gives the spread of a listing's own moves over a horizon and how often they land in the bands the agent means to set, which is what a kept forecast is then scored against, so the playbook has it read before any probability is given. They change only what the app keeps of the agent's own views and reach no order and nothing outside the app, so none goes through the approval gate. A quote is the source's own words only if the conversation read them: before a report or a forecast reaches the desk, each new quote must stand, line by line, in something the conversation's tools returned or its user wrote, which the host reads from the stored transcript (`./provenance` compares them without their spacing, punctuation and markup, and keeps every letter, digit, decimal point and minus). A decisions model reads a claim against its quote, and only this tells that the quote was not made up. A quote the listing's report already holds was read when it was first kept, so it may be sent again. A refused report or forecast fails its call with every reason worded for the model, and nothing is kept. `revise_report` is not safe to run again, since a second run would keep the same revision twice. The `deep-analysis` skill carries how a report and a forecast are worked out; the tools only say what each field holds.
- `./themes` reads and writes the user's themes through the host's `ThemeDesk` from `@solyx/core/theme`. `get_themes` changes nothing, so it never asks, and notes the addresses of the news it shows as `get_news` does. `search_theme` has the host search one theme now, which spends the user's web search as `web_search` does and so never asks either, but searches a theme at most once an hour: a search reaches back past the one before, so one made sooner finds the same items, and a task that runs often would otherwise search more than the user's plan has it. `save_theme` starts a daily search on the user's web search key, so it goes through the approval gate with no auto check, and its arguments are checked before the user is asked. No tool removes a theme.
- `./tasks` reads and writes the user's scheduled tasks through the host's `TaskPort`. `get_tasks` changes nothing, so it never asks. `get_task_runs` reads what a task's runs came to from the conversations they ran in, which the host hands it: where each stands and the reply it closed with, less the canvases it drew, and nothing of any other conversation, so what the user asked the agent elsewhere stays there. A run that asks about its own task reads the runs before it. A run's reply is the model's own earlier words, so `readTexts` leaves the tool's answer out of what a quote may be the words of. `save_task` keeps a message the app then sends the agent on its own, which spends the user's model budget for as long as it stays, so it goes through the approval gate with no auto check: only a conversation the user set to `bypass` keeps one unasked, and a scheduled run, which is never set so, cannot. Its arguments are checked before the user is asked, a theme id `get_themes` does not list among them. A task that waits on a change names the kinds, listings and themes it runs for, every one unless the call names some, and `get_tasks` says what its last run was started for. A task it keeps runs its calls as `auto` unless the call says `ask`, takes the user's own clock and language from the host, and passes the schema the settings page writes through, so it holds no secret. `run_task` starts a task's run now through the host, as the settings' own button does: a whole run on the user's model in a conversation of its own, so it goes through the approval gate with no auto check, like `save_task`, and its call is not safe to run again. It is refused before the user is asked for a task that is not there, one whose last run still goes, and in any conversation a task started, since a run that could start runs could start its own task's next without end. It answers once the run is under way and never waits for it. No tool removes a task.
- `./watchlist` is `change_watchlist`, through the host's `WatchlistPort`; `get_watchlist` reads the list with the trading tools. A watched listing has its news collected on the user's sources and wakes the tasks that wait on a change, so a change goes through the approval gate with no auto check. A call is checked before the user is asked: a listing to add must be one the market data source lists, so a mistyped code is refused, and a call that would change nothing answers so without asking. The prompt keeps the list the user's: the agent changes it only when they ask or agree.
- `./quotes` is `get_quotes`: the newest session of every listing the user holds and watches, or of the ones a call names, through the quote the host's overview reads, with each position marked at its last price as `@solyx/core/order` and `@solyx/core/quote` compute it, so the model cites the app's figures for today's moves and open gains. A listing that cannot be quoted, or an account that cannot be read, is named beside the rest rather than failing the call. It changes nothing, so it never asks.
- `./flows` is `get_flows`: who trades a listing and its market, through the host's `Flows` from `@solyx/core/flows`, with the net buying, runs and changes the app computed, so the model cites them rather than works them out. It changes nothing, so it never asks.
- `./macro` is `get_macro`: the figures of a market's economic indicators over their last periods, through the host's macro module, with the growth on the year the app computed, so the model cites them rather than works them out. It changes nothing, so it never asks. `get_calendar` joins each release's figures from the same reader, read beside the calendar as the overview reads them, and words them the same way, through `./macro-text`.
- `./sectors` is `get_sectors`: Taiwan's market by sector in its newest session, through the host's read of the exchange's sector indices, with the moves and shares of the trading `@solyx/core/sectors` computes and the market's own index from its daily bars, so the model cites what the overview's map shows. Its details carry the sectors as it read them, which the thread maps under the call. It changes nothing, so it never asks.
- `./history` is `search_history`: one search over the research, news and proposals the app kept, through the host's `ResearchDesk`, `NewsDesk` and `ProposingDesk`, so the agent finds what it wrote or read before without knowing where it is kept. It changes nothing, so it never asks, and it notes the addresses of the news it shows as `get_news` does. Memories are searched only with `recall`, which `agent.memory` switches off.
- `./headlines` is `get_headlines`: the heaviest stories across the listings the user holds and watches, or the ones a call names, ranked by the host as its overview ranks them, so the agent's digest and the app's are one list. It reads only the news the app has kept and asks no source, so it costs no request and never asks, and it notes the addresses of the news it shows as `get_news` does.
- `./setup` is `get_setup` and `change_setting`, through the host's `SetupPort`. `get_setup` reads what the user has set up in the app, what is missing and how much each store holds, tab by tab, so the agent answers how the app works from its settings rather than guessing; a key, token or sign-in reaches it only as saved or missing, and it changes nothing, so it never asks. `change_setting` changes one setting to a value the host says it takes: the host decides which, and never a secret, a sign-in or one that widens what the agent reaches. It goes through the approval gate with no auto check, so only `bypass` lets it run unasked, and the host checks it before the user is asked, so a change that cannot be made never asks. The `solyx-guide` skill carries how the app is used and set up, and the prompt never lets the agent ask for a secret in the conversation, since what is written there is kept and sent to the model's provider.
- `./magi` is the council a host may put before the agent's decisions: three units, each a persona on a model the host names, judge alone and at once, and two votes carry a motion. `submit_forecast` and `propose_order` put what they would keep to it only after every other check has passed, so no vote is spent on what would be refused anyway.
  - An order is one motion. A rejected one keeps nothing and comes back with its votes as the call's answer, not as a failed call.
  - A forecast is put as its scenarios, each a motion of its own that the close is more likely to land in its band than the listing's history says, and each unit votes on them all in one answer. The units are shown the bands with history's shares and what the forecast rests on, with how a decisions model read its facts where one did, never the probabilities, direction or plan its author gave, so a vote is a unit's own reading. The forecast is kept however they vote, with each scenario's count, and a listing without base rates is kept without a vote.
  - A unit without a model fails the vote, since that is a setting to fix; a unit still failing after its retries gives no vote, and a motion such missing votes could have carried is undecided rather than rejected, so the agent may put an order again when the user asks. Each ballot is kept in its call's durable memos as it is cast, so a call that runs again after the app's exit counts the same votes and asks only units that had not voted.
  - The vote stands before `propose` and never in place of the user: a carried order still waits for them to confirm it.
- `./traces` traces each run as OpenTelemetry's GenAI conventions name its parts, through pi-durable's generation and tool hooks in an extension the host offers with every run's tools: a span for the run, which the run events the runtime sends open and close, and under it one for each model request and tool call. Spans carry identifiers, models, token counts and cost, never what a conversation says or a tool was given or returned; the host hands it a tracer and decides where spans go.
- The runtime knows no tool by name or origin: the host hands it a `Toolset` (`./toolset`) before every run and before resuming, naming the extensions every request offers and those that wait until the agent loads them. A new source of tools joins where the host builds that toolset, not in the runtime. As the toolset is installed, a tool that names no callers becomes the model's alone, so a script calls only the tools that name scripts among their callers, which the MCP tools alone do, and a deferred extension's tools are pi-durable's deferred ones: enabled, so a script may call them, and offered to the model once it loads them.
- `./approval` is the only way a tool call waits for the user: `guard` wraps any tool, whatever it comes from, and `approve` answers a waiting call. A guarded tool asks about the call its api's `callId` names, which for a script's call is that call's own id. Each conversation has an approval mode, kept with it and `ask` until the user changes it: `bypass` lets that conversation's guarded calls run unasked, shell commands included; `auto` lets a call run unasked only when the check its tool was guarded with says so, which today is the shell's, `read_page`'s and `remember`'s, and a tool guarded without one still asks. A check that fails or cannot answer means the user is asked, and a call it let run is stored and shown as the model's, not the user's. Nothing but the user's own choice sets a conversation's mode. The question and its answer are stored in the conversation before their events go out, after the call's start, so a transcript read from storage shows them. A question is asked in memory: one withdrawn with its run, or left open when the app quits, stays unanswered and its call does not run.
