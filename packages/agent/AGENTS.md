# `@solyx/agent`

The trading agent on pi (`@earendil-works/pi-durable` and `pi-ai`): its runtime, tools, prompt and skills, and the wire events a renderer folds into a conversation.

## Boundaries

- Everything but `./wire`, `./providers`, `./skill-source` and `./mcp-config` runs only in the main process: it holds API keys and calls providers. Those four import nothing from pi or Node, so the renderer uses them for the event union, tool names, the fold, the provider and thinking choices, skill sources and the MCP file.
- Tools read through `TradingToolPorts`, whose desk is a `ProposingDesk`: they may propose, check and read the account, never `confirm`; see the trading invariants. Tools are installed once rather than built per run, so `propose_order`'s one proposal per run is claimed in the conversation's durable state.
- Keys come only from the settings the user saved: `createModelCatalog` owns every call into pi-ai's model catalog (resolving the user's model, an unknown one as the provider's default, and the subscription sign-ins), gives pi-ai an auth context with no environment or files, and pi-ai resolves every request's credential in the host's `CredentialStore`: the saved API key, or the subscription sign-in, which it refreshes, while the user runs on one. OpenAI signs in through `./chatgpt-oauth`, the app's own Sign in with ChatGPT flow, in place of pi-ai's, so OpenAI's consent screen names Solyx and the browser lands on the host's page; it follows OpenAI's guide for open-source, locally hosted apps, and pi-ai's other OAuth flows are never loaded.
- A conversation runs on its own model and thinking level where the user picked them, kept with the conversation, and otherwise on the host's default. The host resolves the pick before every run and refuses one it cannot run, such as a model of a provider the user switched off, rather than run another model in its place.
- Conversations run on pi-durable's Harness over the store `@solyx/db/agent` opens. pi-durable stores every message, the reply streaming and each tool call before anything is shown, and the runtime sends wire events from what it stored. The system prompt is sections rendered before every request, and only a section that changed is stored and sent again.
- The app's per-turn context (time, sessions, account mode, the listing on screen, the reply language) rides in the user message as an `<app_context>` block rather than in the system prompt, so the prompt stays cacheable and a replayed transcript sends the same bytes. `userText` strips it for display.
- A run the app's exit cut off continues once `resume` runs at the next start. A tool call it cut off runs again only when its tool is declared `replay: "safe"`; otherwise the model is told the call was interrupted. Only tools that change nothing are safe, plus `propose_order`, whose call keeps its proposal id in a durable memo so the desk returns the proposal already made under it, and an MCP tool its user lets run without asking.
- Skills come from three places, and a name taken by an earlier one hides later ones: the user's own `skills/` in the config folder, the built-ins in `skills.ts`, then `~/.agents/skills`, whose skills are offered only once the user switches them on. `loadSkillCatalog` reads each folder's `<name>/SKILL.md`, and the prompt's skills section and `read_skill` read the catalog for every request. Files can add playbooks, standing instructions (`AGENTS.md`) and scripts the shell may run, never tools: the tools stay in code, so `propose` remains the agent's only road to an order.
- `./shell` is pi-durable's `bash` on the user's computer (PowerShell on Windows), with no sandbox, and the only way a skill's scripts run. It exists only while the host puts it in the toolset. Every command goes through the approval gate, and only its conversation's approval mode lets one run unasked: in `auto`, the host's decisions model judges the command, and it runs when every risk it scores is unlikely; a command starts in its conversation's own folder with the environment `./process-env` gives a stdio MCP server, never the app's. A command the user allows can still reach anything their account can, including the app's files, so the host offers the shell only beside a paper account, and `read_skill` names a skill's folder only while the shell is offered.
- `./mcp` connects the servers in `mcp.json` through pi-mcp. Their tools wait until the agent loads them: every request offers the app's own tools and `search_tools`, which finds MCP tools by what they do and loads them into the conversation's stored tools with pi-durable's `addTools`, so until then only the list of servers reaches the model: each server's name, its tool count and the `description` the user may write for it in `mcp.json`, or else the name the server gives itself. Nothing else a server says about itself, such as its instructions, reaches the prompt. A stdio server starts with the user's home, name and shell, the login shell's `PATH` and what its entry names, never the rest of the app's environment. Each tool runs under the user's policy: off, ask (each call goes through the approval gate) or auto, which holds only for tools their server marks read-only. MCP tools can reach anything outside the app, so the prompt treats every tool's output as data, never instructions. A remote server that answers 401 waits for the user to sign in: `signIn` runs pi-mcp's OAuth flow (discovery, dynamic client registration, PKCE) through the host's browser and a loopback callback, and hands the grant to the host to keep. Only a sign-in the user starts opens the browser; a connection whose grant can no longer be refreshed waits for the next one. Model and MCP sign-ins alike run one at a time: a new one cancels the one still open, and a cancelled one ends quietly.
- `./analysis` runs the agent's own JavaScript in a QuickJS VM (pi-codemode), on a worker thread with a deadline and a memory limit. A script can call only the functions `createAnalysis` gives it, which read market data and the account and compute the app's indicators; it has no network, files, timers or modules, and no function it can call changes anything. That is why its calls need no approval: a function that proposes, calls an MCP tool or reaches outside the app never joins that list. What a script stores for the conversation's later scripts is kept in the conversation.
- The runtime knows no tool by name or origin: the host hands it a `Toolset` (`./toolset`) before every run and before resuming, naming the extensions every request offers and those that wait until the agent loads them. A new source of tools joins where the host builds that toolset, not in the runtime.
- `./approval` is the only way a tool call waits for the user: `guard` wraps any tool, whatever it comes from, and `approve` answers a waiting call. Each conversation has an approval mode, kept with it and `ask` until the user changes it: `bypass` lets that conversation's guarded calls run unasked, shell commands included; `auto` lets a call run unasked only when the check its tool was guarded with says so, which today is the shell's alone, and a tool guarded without one still asks. A check that fails or cannot answer means the user is asked, and a call it let run is stored and shown as the model's, not the user's. Nothing but the user's own choice sets a conversation's mode. The question and its answer are stored in the conversation before their events go out, after the call's start, so a transcript read from storage shows them. A question is asked in memory: one withdrawn with its run, or left open when the app quits, stays unanswered and its call does not run.
- Prompts and built-in skills are written for Solyx. Do not copy prompt or skill text from other projects whose licenses differ.
