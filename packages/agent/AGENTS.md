# `@solyx/agent`

The trading agent on pi (`@earendil-works/pi-agent-core` and `pi-ai`): its runtime, tools, prompt and skills, and the wire events a renderer folds into a conversation.

## Boundaries

- Everything but `./wire` and `./providers` runs only in the main process: it holds API keys and calls providers. Those two import nothing from pi, so the renderer uses them for the event union, tool names, the fold and the provider and thinking choices.
- Tools read through `TradingToolPorts` and may only call `OrderDesk.propose` and `check`, never `confirm`; see the trading invariants. `propose_order` accepts one proposal per run, so tools are built again for every run.
- Keys come only from the settings the user saved: `createModelCatalog` gives pi-ai an auth context with no environment or files. A run on an API key passes it explicitly; a run on a subscription passes none, so pi-ai resolves and refreshes the sign-in in the host's `CredentialStore`. OpenAI signs in through `./chatgpt-oauth`, the app's own Sign in with ChatGPT flow, in place of pi-ai's, so OpenAI's consent screen names Solyx and the browser lands on the host's page; it follows OpenAI's guide for open-source, locally hosted apps, and pi-ai's other OAuth flows are never loaded.
- A conversation persists through `AgentSessionStore`, which `@solyx/db/user` implements. Each message is stored on pi's `message_end`, before its event goes out, and only user, assistant and tool result messages are kept; the system prompt is rebuilt for every run.
- The app's per-turn context (time, sessions, account mode, the listing on screen, the reply language) rides in the user message as an `<app_context>` block rather than in the system prompt, so the prompt stays cacheable and a replayed transcript sends the same bytes. `userText` strips it for display.
- A run that never finished, because the app exited, replays as `interrupted`, and its calls without results as aborted; nothing resumes it.
- Skills come from three places, and a name taken by an earlier one hides later ones: the user's own `skills/` in the config folder, the built-ins in `skills.ts`, then `~/.agents/skills`, whose skills are offered only once the user switches them on. `loadSkillCatalog` reads the folders through pi-agent-core's `loadSourcedSkills`, and the system prompt and tools are rebuilt from the catalog for every run. Files can add playbooks and standing instructions (`AGENTS.md`), never tools: the tools stay in code, so `propose` remains the agent's only road to an order.
- `./skills` loads files through pi, so the renderer imports only its types.
- `./mcp` connects the servers in `mcp.json` through pi-mcp and offers their tools under the user's policy per tool: off, ask (each call waits on the host's `allow`) or auto, which holds only for tools their server marks read-only. MCP tools can reach anything outside the app, so the prompt treats every tool's output as data, never instructions. A remote server that answers 401 waits for the user to sign in: `signIn` runs pi-mcp's OAuth flow (discovery, dynamic client registration, PKCE) through the host's browser and a loopback callback, and hands the grant to the host to keep. Only a sign-in the user starts opens the browser; a connection whose grant can no longer be refreshed waits for the next one. `./mcp-config` is the renderer-safe half: the file schema, policies and `secret:NAME` references.
- Prompts and built-in skills are written for Solyx. Do not copy prompt or skill text from other projects whose licenses differ.
