# `@solyx/agent`

The trading agent on pi (`@earendil-works/pi-durable` and `pi-ai`): its runtime, tools, prompt and skills, and the wire events a renderer folds into a conversation.

## Boundaries

- Everything but `./wire`, `./attachment`, `./providers`, `./skill-source` and `./mcp-config` runs only in the desktop's backend, which holds API keys and calls providers. Those five import nothing from pi or Node, so the renderer may import them.
- Tools read through `TradingToolPorts`, whose desk is a `ProposingDesk`: they may propose, check and read the account, never `confirm`. `get_calendar` reads the host's calendar through the port the overview reads, so the agent's dates and the app's are one list. Tools are installed once rather than per run, so `propose_order`'s one proposal per run is claimed in the conversation's durable state.
- The providers are pi-ai's built-in ones that run on a single key, by pi-ai's id: `createModelCatalog` withholds the rest (cloud credentials on this computer, more fields than a key, a sign-in the app does not keep), and a test fails when a provider it offers asks for more than one key or, signing in alone, for any. Of pi-ai's own sign-ins it keeps only xAI's, Meta's and GitHub Copilot's, whose flows run on a code the user enters on the provider's page, open no listener and read nothing from the environment, and strips every other. pi-ai's flows are all registered up front, since a bundled backend cannot load one by its file, so every flow's module loads but only a kept provider's can run; only a built app, not a test, shows a flow loads. GitHub Copilot runs on its sign-in alone: the catalog strips its key, signs in to github.com only and lists the models the account has, so a default or a pick the account lacks reads as its first model. `./providers` holds only the id's shape; the renderer learns the providers, and each one's default model, from the host.
- Ollama is the app's own provider, `./ollama`: a server the user runs, which takes no key unless a proxy in front of it checks one. It lists the server's models that chat, call tools and hold the agent's prompt, tools and pi-durable's reserve with room for a conversation, and only when the host asks for the servers the user switched on, so a server nobody uses is never reached. It replies through Ollama's own `/api/chat`, the only API that takes a context length with each request: every request asks for the window pi-durable compacts in and forbids Ollama's own truncating, which would drop the oldest messages unseen. Its list is kept in the host's `ModelsStore` and restored before runs resume, so a conversation finds its model while the server is not answering.
- `createModelCatalog` owns every call into pi-ai's model catalog and gives pi-ai an auth context with no environment or files, so keys come only from the user's saved settings: every request's credential resolves in the host's `ProviderCredentials` (the saved key or the sign-in, which the catalog refreshes). Where all of a provider's models share one endpoint, they use the one the host names, read for every request. OpenAI signs in through `./chatgpt-oauth`, the app's own Sign in with ChatGPT flow, so OpenAI's consent screen names Solyx. OpenRouter signs in through `./openrouter-key`, OpenRouter's flow for apps, which ends in a key the host saves as the provider's API key, so OpenRouter never runs on a sign-in. Both wait on `./sign-in-callback`'s listener, bound to `127.0.0.1` and open only while its sign-in waits, which heeds only a return its flow verifies (the sign-in's state or a path only the provider was sent), so another program or page cannot end a sign-in. A sign-in by code hands the host its code to show, and the catalog opens only an https page a flow names.
- A conversation a scheduled task started keeps that task's id and name in a doc of its own, which only the host sets as it makes the conversation, so a renderer's setup never claims one. Its messages carry a `scheduled` line in their context, and a `changed` line for each change that is why the task runs. Its approval gate is any conversation's: a call that must ask waits for the user. Nobody watches such a run, so it takes at most the tool rounds its task sets, which the host hands in: the round that reaches the bound runs its tools and the run ends as `turn-limit`, which `continue` carries on for as many rounds again.
- A conversation runs on the model and thinking level the user picked for it, else on the host's default. The host resolves the pick before every run and refuses one it cannot run, such as a model of a provider switched off, rather than run another in its place.
- Where the host asks for it, `./title` names a conversation once a run has answered, by the model the host names for that or else the conversation's own: a pi-durable task started after the answer that survives a restart, shown the user's message without the app's context and the answer's opening, and told to treat both as material to name. Until then, and where the provider fails or the model cannot run, a conversation goes by its first message's first line; no other model names in its place. The run is over for the thread as it answers, so the task holds nothing up: the next message, a continue or a summary ends it, and the next answer names the conversation instead. Its request is not counted in the conversation's usage.
- Conversations run on pi-durable's Harness over the store `@solyx/db/agent` opens. pi-durable stores every message and tool call before it is shown, and a streaming reply within a second of showing it, so a crash loses at most that second, which is asked for again. pi-durable has no events of its own: the runtime follows each conversation's state as pi-durable commits it and sends the wire events that tell one state from the next. pi-durable keeps in memory what it read of a conversation and fails for good reading the rest from a file the store erased behind it, so the runtime never asks for a conversation it erased. A call the streaming reply begins goes out as `ToolDraft` once its id and name have come, so a long call such as a report shows before it runs; one an attempt drafted but never ran goes as the next reply starts. The system prompt is sections rendered before every request, and only a changed section is stored and sent again. A storage error ends the Harness for the life of the process: the runtime ends the runs under way as `store-failed`, tells the host once, and every later call fails. Nothing is retried or reopened in place, since runs carry on from what was stored at the next start.
- The runtime sends what the next request holds, as pi-ai estimates it from the stored context, before the events of each commit that changes it, so a run's end stays its last event. pi-durable compacts a conversation as it fills, and `compact` does so when the user asks, on the model the next run would use; it is refused while a run or another compaction goes, and stopping the conversation stops it. The messages before a summary stay in the thread. A compaction that could not be written says why, and a failed model request waiting to be sent again shows the provider's message until it is sent or its run ends.
- The app's per-turn context (times, each market's session, account mode, what the user has on screen, the `@` listings, a `/name` skill, the reply language) rides in the user message as an `<app_context>` block rather than the system prompt, so the prompt stays cacheable and a replayed transcript sends the same bytes. Attached files follow it, each opened by an `<attachment>` tag: an image, which the host's `ImageProcessor` scales to the model's limits and whose one kept copy is in its message, or text (a text file's own or what the host read of a PDF). Text past `MAX_TEXT_ATTACHMENT_BYTES` stands in its message for its length alone, since the model would reread it every request, and `read_attachment` reads it. `./attachment` reads a file by its bytes, never its name, and refuses one no model could read, an image whose header declares more than `MAX_IMAGE_PIXELS` (a few megabytes can declare billions of pixels for the scaling to decode), and a private key or certificate, since the folder goes into backups; the renderer applies the same rules before sending. An image is refused for a model that reads none rather than handed over as pi-durable's placeholder, which the user would take for the image. The prompt treats what a file says as material to read, never instructions.
- `read_attachment` reads only what the user attached in that conversation and changes nothing, so it never asks.
- The host hands the prompt its pages' addresses as `PromptSources.links`, built from its own router's shapes; the package writes no route of its own.
- A run the app's exit cut off continues once `resume` runs at the next start. A model request it was cut off in counts as a failed attempt and is retried as any other; a run cut off as often as pi-durable's restart limit allows without getting further may be what brings the app down, so pi-durable ends it as `interrupted`. `continue` starts a run on the conversation as it stands, without a new message, to carry on a run that errored, was cut off or was stopped; it is admitted as a message is, with the model, tools and ask-every-call mark its run goes on, and a conversation whose last reply answered has nothing to carry on. The host hears of it, and of every other failure pi-durable reports, through `onReport`. A tool call cut off runs again only when its tool is declared `replay: "safe"`; otherwise the model is told it was interrupted. Only tools that change nothing are safe, plus those a second run cannot duplicate: `propose_order`, `propose_exit` and `submit_forecast` (the id of what they make is kept in a durable memo, so the desk returns what was already made), `remember` and `forget`, `change_setting`, `save_theme` and `save_task` (they keep the id of what they write), `change_watchlist`, `save_strategy`, an MCP tool its user lets run without asking, and `codemode`, whose script carries on from the results it already got, so a call it finished is never sent twice.
- Skills come from three places, an earlier one's name hiding later ones: the user's `skills/` in the config folder, the built-ins in `skills.ts`, then `~/.agents/skills`, offered only once the user switches them on. `loadSkillCatalog` refuses a `SKILL.md` whose frontmatter names it other than its folder, since a skill is switched on by its folder but hides others by its name, so it could otherwise stand in for one the user chose. The user may ask for a skill with a leading `/name` unless its frontmatter sets `user-invocable: false`, which marks background the agent reads on its own. A name `AgentCommand` holds, such as `compact`, is the app's own and never reaches the agent. `./wire`'s `messageParts` is the one grammar for what a message names: the host resolves it and the renderer marks it. Files can add playbooks, standing instructions (`AGENTS.md`) and scripts the shell may run, never tools: the tools stay in code, so `propose` remains the agent's only road to an order.
- A reply draws figures as a canvas, an `html` fence the host draws in a frame that runs no script. The `canvas` skill leaves each figure's look to the classes the host's stylesheet draws, so that playbook and the stylesheet change together.
- `./shell` is pi-durable's `bash` on the user's computer (PowerShell on Windows), and the only way a skill's scripts run. It exists only while the host puts it in the toolset. Every command goes through the approval gate, and only its conversation's approval mode lets one run unasked: in `auto`, the host's decisions model judges the command, and it runs when every risk it scores is unlikely. A command starts in its conversation's own folder with the environment `./process-env` gives a stdio MCP server, never the app's. A command the user allows still reaches more than the desk lets the agent, so the host offers the shell only beside a paper account, and `read_skill` names a skill's folder only while the shell is offered.
- `./sandbox` is the app's one sandbox, sandbox-runtime's profile, which the host makes once and hands to the shell and to the runs of the user's strategies: Seatbelt on macOS, bubblewrap with its seccomp filter on Linux. Windows has none, since sandbox-runtime's needs an install as administrator, so there a command runs with the user's own access, as it does where the user switched the sandbox off (the host's switch, on by default and read for every command and every prompt). While it is on, a command it cannot start, such as for a Linux tool missing among the reasons `sandboxProblems` gives, fails with them rather than run unsandboxed; a missing seccomp filter counts, since without it a command reaches the session bus and the keyring behind it. A sandboxed command writes only in its folder, which is also its HOME and holds its TMPDIR; reads nothing of the home, the app's folders or the system's places of other apps' files (`/tmp` and `/var/tmp`, denied by their real paths since on macOS `/tmp` is a link whose denial would deny every path through it; on macOS every app's temporary folder and mounted volumes; on Linux the user's runtime folder and mounted media) but the folders of the skills offered and of the tools on its PATH under the home; and reaches no network, this computer included, since sandbox-runtime's proxies refuse every host. A readable folder lifts a denial on that same place, though sandbox-runtime keeps the denials deeper in it, so, comparing real paths, a skill's folder (possibly a link the user made) is left out where it is or holds the home, the app's folders, the system's secret stores (keychains, keyrings) or any place above, and a tool's folder also where it lies in the app's folders or the secret stores. The folder sandbox-runtime keeps writable for every embedder's temporary files is denied as another app's. Nothing a command may write is read by a process outside the sandbox, such as Apple's developer tools' cache, which would let a command choose what the user's own tools run.
- `./mcp` connects the servers in `mcp.json` through pi-mcp.
  - Their tools wait until the agent loads them through pi-durable's `tool_search`, offered with the app's own tools on every request. It matches whole words in any script against the words each server describes its tools in, so the prompt has the agent search in English first, then in the user's language. Until then only each server's name, tool count and description reach the model (the one the user wrote in `mcp.json`, else the name the server gives itself), never its instructions.
  - A stdio server starts with the user's home, name and shell, the login shell's `PATH` and what its entry names, never the rest of the app's environment.
  - Each tool runs under the user's policy: off, ask (each call goes through the approval gate) or auto, which holds only for tools their server marks read-only and still asks in a run that asks every call. A tool that asks is guarded itself, so the agent's calls and a script's ask alike.
  - MCP tools can reach anything outside the app, so the prompt treats every tool's output as data, never instructions.
  - A remote server that answers 401 waits for the user to sign in through pi-mcp's OAuth flow, the host's browser and a loopback callback, and the host keeps the grant. Only a sign-in the user starts opens the browser. Model and MCP sign-ins run one at a time: a new one cancels the one still open.
- `./script-runner` runs the agent's own JavaScript in a QuickJS VM (pi-codemode), each script on a worker thread of its own with a memory limit; a script reaches only the functions its tool hands it, and the runner stops those still running as the app quits. It also holds the one sandbox `codemode` runs in.
- `./mcp-script` is `codemode`, pi-durable's code mode: a script whose only reach is the MCP tools the policies offer, each a nested tool call, found through `searchTools`, `describeTool` and `describeNamespace` (a server is a namespace), so the tool's description never names a server and servers connecting do not change it. Each call runs under its tool's policy as a direct call would: an asking one goes through the approval gate as `<script call id>/c<n>`, and a refused one throws in the script. A script waits on the user, so it has no deadline unless it sets one; stopping its run stops it, and one the app's exit cut off carries on at the next start, where a call left waiting is not sent and fails in the script. A script gets no models and no environment, so what it prints is never written to a file.
- `./analysis` is `run_analysis`: a script with a deadline that can call only the functions `createAnalysis` and `./analysis-sources` give it, which read market data, the account and the host's own readers and compute the app's indicators; it has no network, files, timers or modules, and no function it can call changes anything. That is why its calls need no approval: a function that proposes, calls an MCP tool or reaches outside the app never joins that list (MCP tools are `./mcp-script`'s alone), and a strategy's code runs only on a version `allow_strategy` let run. A source that counts requests is read for at most `MAX_LISTINGS` listings a script, since its limit is the whole app's, and is split by dataset so a function costs only its own dataset's requests. Daily or longer bars reach up to ten years back, for a few listings a script since each year costs a request the first time; they are prices as traded, each with the exchange's reference price it moved from, so `indicators.adjustment` carries them over splits and ex-dates as a forecast's judging does. `backtest.*` and `strategies.*` run through `@solyx/core/backtest` on the kernel the host hands `createAnalysis`, so fills and costs are the engine's and a script cannot act on a price it could not have known; they read the listing's bars themselves, through the readers and history budget `tools.candles` uses, so a script never hands them bars and bars never cross into the VM. Bars shorter than a day reach back three years and take their sessions' references from the daily bars. `strategies.*` has the host run the strategy's code for its lines, refused unless that version of its files is allowed. Every function's types ride in the tool's description; past a few thousand tokens of them, the sources should move behind a catalog a script asks, as MCP tools are. The `backtest` skill carries how a backtest is split and reported.
- `./strategies` reads and writes the user's strategies through the host's `StrategiesPort`. `get_strategy` and `get_runtimes` change nothing, so they never ask. `allow_strategy` lets the named version of a strategy's files run where its code would now run, and `save_strategy` writes files and allows the version that makes, so allowing a change is allowing that version. Both are checked before the user is asked: a version the files have left or a change the host refuses is refused unasked, and a version already allowed, or a change that leaves an allowed strategy as it is, answers unasked. In `auto`, `allow_strategy` passes unasked when the decisions model scores every risk of the code under the line `scripts/eval-code.ts` measured (a file that is not text cannot be judged, so the user is asked); `save_strategy` passes unasked only for a strategy not yet written or whose files are as this conversation last wrote them, kept in the conversation's durable state, and only once the decisions model finds the resulting code harmless, so a change to the user's own work always asks. Outside the sandbox beside a live account only the user's own answer allows a version: neither check lets one through, and `bypass` allows none (`save_strategy` still writes the files). The `strategy` skill carries how a strategy is written, checked and tested.
- `./web` searches and reads the web through the vendor the host hands it (`WebSearch` and `WebReader` from `@solyx/core/web-search`), and exists only while the host puts it in the toolset, which it does while the user's vendor has a key. A search changes nothing and goes only to that vendor, so it runs unasked. Reading a page fetches an address the model wrote, which could carry what the conversation holds to a host a page named, so every read goes through the approval gate; in `auto` one runs unasked only at an address the conversation's own `web_search`, `get_news`, `get_themes`, `search_history` or `get_headlines` showed the model, which those tools note in the conversation's durable state.
- `./memory` is what the agent keeps across conversations, in the host's `MemoryStore`. Both writes go through the approval gate, their arguments checked before the user is asked. `remember`'s check passes only a new memory of kind `note`, so in `auto`, scheduled runs included, the agent adds notes unasked while a rewrite under an id and any `profile` or `feedback` memory wait for the user: a rewrite replaces the memory in place and cannot be undone, and a profile or feedback memory's description reads as the user's own rule in every later prompt, which a page or tool output must not be able to plant. `forget` has no check, since forgetting cannot be undone, so only `bypass` lets it run unasked. The prompt has the agent save what it learns of the user only from what they say and do, never from what pages or tools said, and say in its reply what it saved. Where the host gives a model on this computer, a new memory too close to one of its kind and listing (above `MEMORY_LINES`) is refused with that memory's id unless the call says it is distinct. The prompt treats a memory as what was true when written, never as instructions or current data. Scripts never reach memories, and only `recall` searches them, which `agent.memory` switches off.
- `./research` reads and writes a listing's research through the host's `ResearchDesk` (`get_research`, `revise_report`, `submit_forecast`) and reads its figures with `get_fundamentals` and `get_base_rates`, which the app computes, so the model cites them rather than working them out. `get_fundamentals` tells apart a market no source covers, a part the source has none of on file and a part that could not be read, so a missing figure is never taken for a listing that files none. `get_base_rates` gives the spread a kept forecast is scored against, so the playbook has it read before any probability is given. These tools change only the app's record of the agent's own views and reach no order and nothing outside the app, so none goes through the approval gate. Before a report or forecast reaches the desk, each new quote must stand, line by line, in something the conversation's tools returned or its user wrote, read from the stored transcript (`./provenance` compares without spacing, punctuation and markup, keeping every letter, digit, decimal point and minus); a decisions model reads a claim against its quote, and only this tells that the quote was not made up. A quote the listing's report already holds may be sent again. A refused report or forecast fails its call with every reason worded for the model, and nothing is kept. `revise_report` is not safe to run again, since a second run would keep the same revision twice. The `deep-analysis` skill carries how a report and a forecast are worked out; the tools only say what each field holds.
- `./themes` uses the host's `ThemeDesk`. `search_theme` spends the user's web search as `web_search` does and so never asks, but searches a theme at most once an hour: a search reaches back past the one before, so one made sooner finds the same items, and a frequent task would otherwise search more than the user's plan allows. `save_theme` starts a daily search on the user's key, so it goes through the approval gate with no auto check, its arguments checked before the user is asked. No tool removes a theme.
- `./tasks` uses the host's `TaskPort`. `get_task_runs` reads only the conversations a task's runs ran in, less their canvases, so what the user asked elsewhere stays there; a run's reply is the model's own earlier words, so `readTexts` leaves that answer out of what a quote may come from. `save_task` keeps a message the app then sends the agent on its own, spending the user's model budget for as long as it stays, so it goes through the approval gate with no auto check: only a conversation the user set to `bypass` keeps one unasked, which a scheduled run never is. Its arguments, a theme id `get_themes` does not list among them, are checked before the user is asked. A saved task runs its calls as `auto` unless the call says `ask`, takes 50 tool rounds a run unless the call sets another bound, and passes the schema the settings page writes through, so it holds no secret. `run_task` starts a whole run now in a conversation of its own, so it goes through the approval gate with no auto check and is not safe to run again; it is refused before asking for a missing task, one whose last run still goes, and in any conversation a task started, since a run that could start runs could start its own task's next without end. It never waits for the run. No tool removes a task.
- `./watchlist` is `change_watchlist`, through the host's `WatchlistPort`. A watched listing has its news collected and wakes the tasks that wait on a change, so a change goes through the approval gate with no auto check. A call is checked before the user is asked: a listing to add must be one the market data source lists, and a call that would change nothing answers so unasked. The prompt has the agent change the list only when the user asks or agrees.
- The read tools (`get_quotes`, `search_listings`, `get_flows`, `get_macro`, `get_sectors`, `get_sector_movers`, `get_rotation`, `search_history`, `get_headlines`, `get_themes`, `get_tasks`, `get_setup`) change nothing, so they never ask. Each reads through the host reader the matching app view uses and returns the figures the app computes, so the model cites the app's numbers rather than working them out and the agent's lists match the app's. `get_quotes` names a listing that cannot be quoted, or an account that cannot be read, beside the rest rather than failing the call. `get_headlines` reads only the news the app kept, so it costs no request. `get_calendar` words each release's figures through `./macro-text`, as `get_macro` does.
- `./setup` is `get_setup` and `change_setting`, through the host's `SetupPort`. `get_setup` sees a key, token or sign-in only as saved or missing. `change_setting` changes one setting to a value the host says it takes: the host decides which, and never a secret, a sign-in or one that widens what the agent reaches. It goes through the approval gate with no auto check, so only `bypass` lets it run unasked, and the host checks it before the user is asked. The prompt never lets the agent ask for a secret in the conversation, since what is written there is kept and sent to the model's provider.
- `propose_exit` puts an exit of a held position before the user (a stop, a target or both the broker then watches) and takes the reply's one proposal as `propose_order` does. It is not put to the MAGI: it only sells what the account holds, at prices the user confirms.
- `./magi` is the council a host may put before the agent's decisions: three units, each a persona on a model the host names, judge alone and at once, and two votes carry a motion. `submit_forecast` and `propose_order` put what they would keep to it only after every other check has passed, so no vote is spent on what would be refused anyway.
  - An order is one motion. A rejected one keeps nothing and comes back with its votes as the call's answer, not as a failed call.
  - A forecast is put as its scenarios, each a motion that the close is more likely to land in its band than the listing's history says; each unit votes on them all in one answer. The units see the bands with history's shares and what the forecast rests on, with a decisions model's reading of its facts where one did, never the author's probabilities, direction or plan, so a vote is a unit's own reading. The forecast is kept however they vote, with each scenario's count, and a listing without base rates is kept without a vote.
  - A unit without a model fails the vote, since that is a setting to fix; a unit still failing after its retries gives no vote, and a motion such missing votes could have carried is undecided rather than rejected, so the agent may propose again when the user asks. Each ballot is kept in its call's durable memos as cast, so a call run again after the app's exit counts the same votes and asks only units that had not voted.
  - The vote stands before `propose` and never in place of the user: a carried order still waits for them to confirm it, unless their trading mandate covers it.
- `./traces` traces each run with OpenTelemetry's GenAI conventions, through pi-durable's generation and tool hooks in an extension the host offers with every run's tools: a span for the run, opened and closed by the runtime's run events, and under it one per model request and tool call. Spans carry identifiers, models, token counts and cost, never what a conversation says or a tool was given or returned; the host hands it a tracer and decides where spans go.
- The runtime knows no tool by name or origin: the host hands it a `Toolset` (`./toolset`) before every run and before resuming, naming the extensions every request offers and those that wait until the agent loads them. A new source of tools joins where the host builds that toolset, not in the runtime. A tool that names no callers is the model's alone, so a script calls only tools that name scripts among their callers, which the MCP tools alone do; a deferred extension's tools are pi-durable's deferred ones, enabled so a script may call them and offered to the model once loaded.
- `./approval` is the only way a tool call waits for the user: `guard` wraps any tool, whatever its source, and `approve` answers a waiting call. A guarded tool asks about the call its api's `callId` names, which for a script's call is that call's own id. Each conversation has an approval mode, kept with it and `ask` until the user changes it: `bypass` lets its guarded calls run unasked, shell commands included; `auto` lets a call run unasked only when its tool's guard check says so (the shell's, `read_page`'s, `remember`'s, `allow_strategy`'s and `save_strategy`'s), and a tool guarded without a check still asks. A check that fails or cannot answer means the user is asked, and a call it let run is stored and shown as the model's, not the user's. Nothing but the user's own choice sets a conversation's mode. A message the host marks as asking every call, as it marks a paired device's, has its run ask before every guarded call whatever the mode, and before every call of a tool the user lets run unasked, which passes the gate through `unasked`; the mark is stored in the one commit that admits its message, with the model and tools its run goes on, and only another message's admission changes it, so no run of a marked message runs a call unasked and a message refused as busy leaves the run under way as it was. The question and its answer are stored in the conversation before their events go out, after the call's start. A question is asked in memory: one withdrawn with its run, or left open when the app quits, stays unanswered and its call does not run.
- Tools write the numbers they return through `./figures`, so a change, a part of a whole and a missing figure read alike in every tool: a plus only above zero, a fraction in percent and `n/a` for what the app does not have.
- `scripts/eval-backtests.ts` runs the agent as the app wires it, on real Taiwan bars and the keys in `.env`, and grades each run by what it called and by a judge model reading its reply against the engine's results. The `backtest` skill's rules rest on it: run it again after changing that skill, `backtest.rules` or the prompt's rules on evidence. Requests marked held out were written before the skill was tuned and tell whether a change carries over, so the skill is never tuned on them. What it writes holds market data, so it stays out of the repository.
- Prompts and built-in skills are written for Solyx. Do not copy prompt or skill text from other projects whose licenses differ.
