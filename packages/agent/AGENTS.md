# `@solyx/agent`

The trading agent on pi (`@earendil-works/pi-durable` and `pi-ai`): its runtime, tools, prompt and skills, and the wire events a renderer folds into a conversation.

## Boundaries

- Everything but `./wire`, `./providers`, `./skill-source` and `./mcp-config` runs only in the main process: it holds API keys and calls providers. Those four import nothing from pi or Node, so the renderer uses them for the event union, tool names, the fold, the provider and thinking choices, skill sources and the MCP file.
- Tools read through `TradingToolPorts`, whose desk is a `ProposingDesk`: they may propose, check and read the account, never `confirm`; see the trading invariants. `get_calendar` reads the host's calendar through the same port the overview shows, so the agent's dates and the app's are one list, and the prompt has the agent read it before searching the web for dates. Tools are installed once rather than built per run, so `propose_order`'s one proposal per run is claimed in the conversation's durable state.
- The providers are pi-ai's built-in ones that run on a single key, by pi-ai's id: `createModelCatalog` withholds the rest (cloud credentials on this computer, more fields than a key, sign-in only) and strips every built-in sign-in, and a test fails when a provider it offers asks for more than one key. `./providers` holds only the id's shape, so the renderer learns the providers from the host, and each provider's default model stays behind the catalog.
- Keys come only from the settings the user saved: `createModelCatalog` owns every call into pi-ai's model catalog (resolving the user's model, an unknown one as the provider's default, and the subscription sign-ins), gives pi-ai an auth context with no environment or files, serves a provider's models from the endpoint the host names, read for every request, where all of them share one, and pi-ai resolves every request's credential in the host's `ProviderCredentials`, which the catalog asks one offered provider at a time: the saved API key, or the subscription sign-in, which it refreshes, while the user runs on one. OpenAI signs in through `./chatgpt-oauth`, the app's own Sign in with ChatGPT flow, in place of pi-ai's, so OpenAI's consent screen names Solyx and the browser lands on the host's page; it follows OpenAI's guide for open-source, locally hosted apps, and pi-ai's other OAuth flows are never loaded.
- A conversation runs on its own model and thinking level where the user picked them, kept with the conversation, and otherwise on the host's default. The host resolves the pick before every run and refuses one it cannot run, such as a model of a provider the user switched off, rather than run another model in its place.
- Conversations run on pi-durable's Harness over the store `@solyx/db/agent` opens. pi-durable stores every message, the reply streaming and each tool call before anything is shown, and the runtime sends wire events from what it stored. The system prompt is sections rendered before every request, and only a section that changed is stored and sent again.
- The app's per-turn context (the time on each exchange and on the user's own clock, sessions, account mode, the listing on screen, the reply language) rides in the user message as an `<app_context>` block rather than in the system prompt, so the prompt stays cacheable and a replayed transcript sends the same bytes. `userText` strips it for display.
- A run the app's exit cut off continues once `resume` runs at the next start. A tool call it cut off runs again only when its tool is declared `replay: "safe"`; otherwise the model is told the call was interrupted. Only tools that change nothing are safe, plus `propose_order` and `submit_forecast`, whose calls keep the id of what they make in a durable memo so the desk returns what was already made under it, `remember` and `forget`, whose calls change the same memory again, an MCP tool its user lets run without asking, and `run_tool_script` while every tool it can call is one.
- Skills come from three places, and a name taken by an earlier one hides later ones: the user's own `skills/` in the config folder, the built-ins in `skills.ts`, then `~/.agents/skills`, whose skills are offered only once the user switches them on. `loadSkillCatalog` reads each folder's `<name>/SKILL.md`, and the prompt's skills section and `read_skill` read the catalog for every request. Files can add playbooks, standing instructions (`AGENTS.md`) and scripts the shell may run, never tools: the tools stay in code, so `propose` remains the agent's only road to an order.
- `./shell` is pi-durable's `bash` on the user's computer (PowerShell on Windows), with no sandbox, and the only way a skill's scripts run. It exists only while the host puts it in the toolset. Every command goes through the approval gate, and only its conversation's approval mode lets one run unasked: in `auto`, the host's decisions model judges the command, and it runs when every risk it scores is unlikely; a command starts in its conversation's own folder with the environment `./process-env` gives a stdio MCP server, never the app's. A command the user allows can still reach anything their account can, including the app's files, so the host offers the shell only beside a paper account, and `read_skill` names a skill's folder only while the shell is offered.
- `./mcp` connects the servers in `mcp.json` through pi-mcp. Their tools wait until the agent loads them: every request offers the app's own tools and `search_tools`, which finds MCP tools by what they do and loads them into the conversation's stored tools with pi-durable's `addTools`, so until then only the list of servers reaches the model: each server's name, its tool count and the `description` the user may write for it in `mcp.json`, or else the name the server gives itself. Nothing else a server says about itself, such as its instructions, reaches the prompt. A stdio server starts with the user's home, name and shell, the login shell's `PATH` and what its entry names, never the rest of the app's environment. Each tool runs under the user's policy: off, ask (each call goes through the approval gate) or auto, which holds only for tools their server marks read-only. A tool's one `call` applies its policy, so the agent's calls and a script's ask alike, and scripts reach the tools only through the hub's `McpCatalog`. MCP tools can reach anything outside the app, so the prompt treats every tool's output as data, never instructions. A remote server that answers 401 waits for the user to sign in: `signIn` runs pi-mcp's OAuth flow (discovery, dynamic client registration, PKCE) through the host's browser and a loopback callback, and hands the grant to the host to keep. Only a sign-in the user starts opens the browser; a connection whose grant can no longer be refreshed waits for the next one. Model and MCP sign-ins alike run one at a time: a new one cancels the one still open, and a cancelled one ends quietly.
- `./script-runner` runs the agent's own JavaScript in a QuickJS VM (pi-codemode), each script on a worker thread of its own with a memory limit; a script reaches only the functions its tool hands it, and the runner stops those still running as the app quits.
- `./mcp-script` is `run_tool_script`: a script whose only reach is the MCP tools the policies offer, which it finds with `searchTools` and `describeTool`, so the tool's description never names one and servers connecting do not change it. Each call runs under its tool's policy as a direct call would: an asking one goes through the approval gate as `<script call id>/<n>`, and a refused one throws in the script. A script waits on the user, so it has no deadline; stopping its run stops it. The script's details list its calls, from which the transcript starts and ends each under the script, live and replayed alike.
- `./analysis` is `run_analysis`: a script with a deadline. It can call only the functions `createAnalysis` gives it, which read market data and the account and compute the app's indicators; it has no network, files, timers or modules, and no function it can call changes anything. That is why its calls need no approval: a function that proposes, calls an MCP tool or reaches outside the app never joins that list, and MCP tools are `./mcp-script`'s alone. What a script stores for the conversation's later scripts is kept in the conversation.
- `./web` searches and reads the web through the vendor the host hands it (`WebSearch` and `WebReader` from `@solyx/core/web-search`), and exists only while the host puts it in the toolset, which it does while the user's vendor has a key. A search changes nothing and goes only to that vendor, so it runs unasked. Reading a page fetches an address the model wrote, which could carry what the conversation holds to a host a page named, so every read goes through the approval gate; in `auto` one runs unasked only at an address the conversation's own `web_search`, `get_news` or `search_history` showed the model, which those tools note in the conversation's durable state.
- `./memory` is what the agent keeps across conversations, in the host's `MemoryStore` from `@solyx/core/memory`. The prompt's memory section, read for every request, lists each memory's description, profile and feedback before notes, up to a fixed length, and `recall` reads and searches them all. `remember` and `forget` go through the approval gate with no auto check, so only `bypass` lets one run unasked, and their arguments are checked before the user is asked, so a call that cannot run never asks. A new memory's id is kept in a durable memo, so a call that runs again rewrites what it saved. The prompt treats a memory as what was true when it was written, never as instructions or current data. Scripts never reach memories.
- `./research` reads and writes a listing's research through the host's `ResearchDesk` from `@solyx/core/research`: `get_research`, which also lists the news a decisions model read as stating a falsifier happened, `revise_report` and `submit_forecast`, and reads its filed figures with `get_fundamentals`, which the host's `Fundamentals` serves and the app computes, so the model cites them rather than working them out. They change only what the app keeps of the agent's own views and reach no order and nothing outside the app, so none goes through the approval gate. A refused report or forecast fails its call with every reason worded for the model, and nothing is kept. `revise_report` is not safe to run again, since a second run would keep the same revision twice. The `deep-analysis` skill carries how a report and a forecast are worked out; the tools only say what each field holds.
- `./history` is `search_history`: one search over the research, news and proposals the app kept, through the host's `ResearchDesk`, `NewsDesk` and `ProposingDesk`, so the agent finds what it wrote or read before without knowing where it is kept. Each kind matches as `searchTerms` splits words: research and news through their databases' full-text indexes, proposals in memory, since they are few. Where the host's desks hold a model on this computer, research and news are also ranked by meaning, and the two rankings fused. It changes nothing, so it never asks, and it notes the addresses of the news it shows as `get_news` does. Memories are searched only with `recall`, which `agent.memory` switches off.
- `./magi` is the council a host may put before the agent's decisions: three units, each a persona on a model the host names, judge a motion alone and at once, and two votes carry it. `submit_forecast` and `propose_order` put what they would keep to it while the host hands them one, only after every other check has passed, so no vote is spent on what would be refused anyway. A rejected motion keeps nothing and comes back with its votes as the call's answer, not as a failed call. Every unit's model is resolved before any is asked, and a unit without one fails the vote, since that is a setting to fix. A unit whose provider fails is asked again after a pause, and one that answers with no readable vote is shown its answer and asked again; only one still failing after its retries gives no vote, counting for neither side. A motion such missing votes could have carried is undecided rather than rejected: it keeps nothing either, but the agent may put it again when the user asks, without spending its one revision. Each vote is kept in its call's durable memos as it is cast, and the count once it is made, so a call that runs again after the app's exit counts the same votes and asks only units that had not voted; an order already proposed under the call shows the vote it kept. The vote stands before `propose` and never in place of the user: a carried order still waits for them to confirm it. The personas are written for Solyx.
- The runtime knows no tool by name or origin: the host hands it a `Toolset` (`./toolset`) before every run and before resuming, naming the extensions every request offers and those that wait until the agent loads them. A new source of tools joins where the host builds that toolset, not in the runtime.
- `./approval` is the only way a tool call waits for the user: `guard` wraps any tool, whatever it comes from, and `approve` answers a waiting call. A guarded tool asks about the call its api's `callId` names, which for a script's call is that call's own id. Each conversation has an approval mode, kept with it and `ask` until the user changes it: `bypass` lets that conversation's guarded calls run unasked, shell commands included; `auto` lets a call run unasked only when the check its tool was guarded with says so, which today is the shell's and `read_page`'s, and a tool guarded without one still asks. A check that fails or cannot answer means the user is asked, and a call it let run is stored and shown as the model's, not the user's. Nothing but the user's own choice sets a conversation's mode. The question and its answer are stored in the conversation before their events go out, after the call's start, so a transcript read from storage shows them. A question is asked in memory: one withdrawn with its run, or left open when the app quits, stays unanswered and its call does not run.
- Prompts and built-in skills are written for Solyx. Do not copy prompt or skill text from other projects whose licenses differ.
