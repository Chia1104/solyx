# `@solyx/backend`

The app's backend, composed in `services.ts`. The desktop runs it in a utility process of its own, started from `apps/desktop/src/utility/backend.ts`, and it reaches Electron only through the `Host` port in `host.ts`. Rules that span it, the desktop's main process and the renderer, such as how windows reach the router, live in [`../../apps/desktop/AGENTS.md`](../../apps/desktop/AGENTS.md).

## Layout

- `modules/<module>/`: the module's logic and its procedures in `<module>.route.ts`, ending in `<module>Router`, built on `contractOS` from `rpc/context.ts`, or on `implement(<module>Contract)` over a context of its own, the part of the services it reads, where its tests need no more, as `settings` does. What only the process running the backend can do reaches a module through a small port, so it is tested without it.
- `rpc/`, `scheduler.ts`, `services.ts`: the oRPC context, router and server; the one clock for periodic work; the composition root.
- `host.ts`: the `Host` port, everything the services ask of the process that runs them, such as its folders, the secret store's cipher, Fubon's process, the windows and the tray. Lint keeps `electron`, `electron-updater` and `@sentry/electron` out of every package, so the backend never depends on the process it runs in.
- `worker/<name>.ts`: a worker thread's entry, which the app running the backend builds as its own bundle beside the backend's, since a thread starts from a file, with the message contract the backend starts it with where it has one. The agent's scripts run in one, and each backup and restore in another.

## Settings and secrets

- `userData` holds secrets, caches and each database as its own file. Settings live in `~/.<app-name>/config.json` (`~/.solyx`, `~/.solyx-dev`, …), JSON a person may edit. Its `$schema` names the `config.schema.json` beside it, which the app generates from the zod schema it reads with and rewrites at start when it differs, so the file carries no comments and that schema documents every entry. The backend watches the file and applies saved edits without a restart, keeps entries it does not read when saving, reads an entry that no longer parses as its default and replaces it when saving beneath it, and never overwrites a file with syntax errors.
- The config folder also holds what the user writes for the agent, read afresh for every run: `skills/`, `AGENTS.md` and `mcp.json`, whose secrets are named `secret:NAME` and kept in the secret store. A skill shared through `~/.agents/skills` is offered only once it is listed in `agent.sharedSkills`.
- The config file and the secret store tell their listeners about every change, the app's own and a hand edit alike, so each module follows what it reads and a handler only saves.
- Secrets (provider keys, and the OAuth tokens of subscription and remote MCP sign-ins) are saved as ciphertext in `userData` with Electron's async `safeStorage`, which the backend reaches through the main process, and decrypted only when a provider needs one. pi-ai and pi-mcp read and refresh them through a `CredentialStore` over the secret store. Where the OS has no secret store (Linux `basic_text`), nothing is saved.
- The renderer can save or delete a key and start, cancel or end a sign-in, but never reads a key back or sees a token.

## Devices and the edge

- The edge (`modules/devices/edge.ts`) is Hono on Node, listening on `127.0.0.1` at `remote.port` only while `remote.enabled` is on, and following both as they change. It answers only a request whose `Host` names this computer (`localhost`, `127.0.0.1`, `[::1]`, at any port, since `ssh -L` picks one), so a page that rebinds its own name to this computer reaches nothing, and takes a pairing or a socket only from a page it served itself (`Origin`).
- A browser pairs with a code the settings page shows, which lasts five minutes, works once and is gone after five wrong tries. The device's token is told only to that browser; the backend keeps its SHA-256, with each device's name, sealed in the secret store, so no edit of the app's files pairs one.
- A paired browser opens `/rpc` with its token beside the `solyx` subprotocol, since a browser sets no header on a WebSocket, and is served the router as `client` `{ kind: device }`. One that is not paired, or is unpaired while connected, is closed with `UNPAIRED_CLOSE_CODE`. Every procedure is refused to a device unless its contract marks it for devices, checked before its input is read, so a device never confirms, cancels at the broker, answers the agent's calls, unseals or changes settings.

## Agent

- MCP servers in `mcp.json` run as the backend's child processes or are reached over HTTP, and close when the app quits; `@solyx/agent` owns how they connect.
- The agent's models come from the providers the user switched on in `agent.providers`, plus the default model's provider, which is always on. An id the catalog no longer offers reads as switched off, and a default provider it no longer offers as the app's default one; each provider's key is the secret `<provider-id>-api-key`. `createAgentModels` reads and writes every setting that names a provider, and refuses an id the catalog does not offer before anything is saved for it. `agent.provider`, `agent.model` and `agent.thinking` name the default a conversation runs on until it picks its own, and a provider's models run only once its key is saved or its subscription signed in. `agent.auth` says, provider by provider, which of the two it runs on, a key unless set otherwise, and a subscription's sign-in is the secret `<provider-id>-sign-in`. GitHub Copilot takes no key, so it runs on its sign-in whatever `agent.auth` says. OpenRouter's key may come from a sign-in to it instead, saved as the same secret. `agent.endpoints` sends a provider's requests to the endpoint the user set in place of its own, on an API key only: a sign-in's tokens go to the provider's own endpoint and nowhere else. Ollama, a server the user runs, takes no key, and its secret is sent only where the user saved one for a proxy; it runs once it lists a model that can run the agent. It is asked for its models only once switched on, again whenever its endpoint or key changes and while its settings show, and windows are told only when what it lists changed, since a window reading it asks again. The list it gave last is kept in `userData/agent-models.json`, restored before runs resume, and served from the endpoint set now, this computer's included.
- The agent reads the settings through `agent-setup.ts` as the settings page's own readers give them, and a secret reaches it only as its state; the readiness checks it shares with first-run setup sit in `@solyx/api/settings`. It changes only the settings `agent-setup.ts` lists, through the writers the settings page uses: the appearance, Taiwan's source and the data plans, the default provider, model and thinking, the decision mode, each collection's switch and hourly span, the web search, decisions and embeddings providers and update checks. A key, a sign-in, a provider switched on, an endpoint, the shell, MCP tool policies, shared skills, memory, the tray, where backups go, the account orders go to, the trading mandate and the lock on orders stay the user's alone, since each would widen what the agent reaches. It reads what each store holds through the storage module's `usage`, the one the storage tab shows, and never clears one: clearing is the user's, on that tab.
- The addresses the agent links to, a settings section's, an overview tab's and a listing's page, are built in `@solyx/api` beside the shapes the router reads them with, so a reply's link and the router cannot drift apart.
- What the window showed as a message was written reaches the agent in words: `message-context.ts` names each chart indicator as the agent's tools name it and each overview tab by what it shows, so the context never carries the renderer's own ids.
- Before a message's context is written, the agent module resolves its `@` codes against the listing on screen and the watchlist, reading the account's holdings only for a code those miss, since a live broker answers over the network, and its leading `/name` against the offered skills the user may ask for. A token that names neither stays the user's text, and a source that fails leaves out only what it knew.
- The agent's shell is off until `agent.shell` is switched on, and stays off whatever that says while the desk trades a live account. Each conversation's commands work in its own folder under `userData/agent-workspaces`, erased with the conversation.
- The memory module shares one `MemoryStore` over `memory.sqlite`, which tells every window after each write, whether the agent's, the settings page's or clearing them all. Deleting a conversation keeps what it saved, since a memory is kept for the conversations after it. The agent gets its memories from its next run on while `agent.memory` is on, which it is until the user switches it off; switched off, they stay saved.
- `agent.decisionMode` says who judges the agent's forecasts and order proposals: the agent alone, or the MAGI, which votes an order up or down and votes on each of a forecast's scenarios. Under the MAGI each unit answers on the model `agent.magi` names for it, or else on the model of the conversation that put the motion, and each turn's context tells the agent the mode.
- Sign-in callbacks: Sign in with ChatGPT listens on port 1455, a remote MCP server's sign-in on the port its client registration redirects to, and each takes any free port when that one is taken; OpenRouter's sign-in listens on any free port. A sign-in that runs on a code opens no listener: the settings module pushes the code to the windows.
- Once the conversations' store fails, the agent module reports it, tells every window, and answers so to any window that asks later; a window then offers a restart in place of the composer. The app restarts by quitting as it always does, so what is open closes first. Orders are not held up: the desk keeps its own database.

## Windows and the tray

- While `tray.show` is on, the app keeps an icon in the menu bar or the system tray and stays open there once its last window closes, so the clock's work goes on; off, it quits with its last window, except on macOS, where it stays in the Dock. `tray.hideDock` takes it out of the Dock only while no window is open and the icon is there to bring it back.
- The tray module decides what the icon and the Dock show through the `Host` port, and the main process draws them, telling the backend how many windows are open and which row was picked. Its menu lists what waits for the user (proposals to confirm and conversations with a call to allow, counted beside the icon), the scheduled tasks running and next, and an update to install. Whatever tells the windows of a change to one of those tells the tray, which then reads them all afresh. The menu belongs to no window, so a row opens the window at its place through the workspace module and never confirms an order or answers an approval itself.
- The agent module knows which conversations have a call waiting from its runs' events alone, since a question lives only as long as its run.
- The inbox module lists what waits for the user on the overview's Today tab: the proposals to confirm and the conversations with a call to allow, read as the tray's menu reads them, and the reports of the listings the user holds and watches with something to take in, through `ResearchDesk.backlog`. It reads only what the app keeps and the account, keeps nothing of its own, since each item leaves once it is handled, and tells windows whenever a proposal, a waiting call, research or the watchlist changes.

## Markets and providers

- The watchlist module is the one writer of the listings the user watches, over the user's database, and tells every window after each change, whether a window's, the agent's or clearing them all.
- What is read from a provider on demand and kept for a while, such as a market's trading days and schedule of economic releases and a listing's fundamentals, goes through `keepFresh` from `@solyx/utils/fresh`, its freshness beside the call and its answers kept in `cache.sqlite` under a scope of its own, so a restart within the freshness costs no request, and readers that come during an ask share it. Such reads never move onto the scheduler: a prefetch spends a provider's limit with nobody looking.
- Market data providers enforce the limits of the user's plan, so the backend keeps one provider per credential and plan. The config file picks each market's source; the market module follows the settings and keys, reopens the stream when they change and tells windows to load and watch again. It keeps a listing's names for the session once a source finds them, since news groups stories by them on every read.
- A listing's quote reads the five-minute series a chart of that interval reads, through the candle cache and never the stream, so the symbols pane and the overview's heat map leave the stream's subscriptions to charts and books and cost one intraday request per refresh; the agent's `get_quotes` reads the same quote. Taiwan's sectors cost a request per sector index, since the basic plan has no market snapshot, so they refresh at a slower pace and only while shown. The agent's `get_sectors` reads them through the same call, whose answer is kept for a minute, so the map and a call share one read. The rotations module reads every rotation over three years of daily bars through the candle cache, the weekly readings merged from them, the agent's as of the newest session or any of the last `PLAYBACK_SESSIONS`, and the overview's graphs as each path across those sessions, read once and played back in the window, with the benchmark's closes where every entry shares one; every index's and listing's bars are kept in memory while the exchange's day and session they were read in last, and five minutes at most through the regular session, with every path worked out from them afresh, so a change of benchmark and `get_rotation` cost no request between; listings' rotations are read on request, a daily-bar request per listing and one per market for its index, for what the user holds and watches, for a listing's page against its own sector's index, whose industry the exchange's list gives, and for the listings the agent names, each against its market's index, its own sector's or one benchmark; the sectors too may be read against a TWSE benchmark, and a benchmark other than the market's index is refused with why unless it qualifies. The renderer refreshes quotes and sectors only through the market's regular session, and once more as its after-hours session opens.
- The `live-candles` hub keeps each watched symbol's session of minute bars from a `MarketDataStream`, and a symbol a restarted stream refuses ends the watches that followed it, folds them into the intervals windows watch and pushes whole bars, so the renderer only upserts them by time. Each `market.liveCandles` stream is one watch, which ends with it, and the symbol stops being live once its last watch ends. Only today's session is pushed; closed sessions come from history through the candle cache. A chart starts from its interval's lookback window and, as it is scrolled to its oldest bar, reads the page of history before it, until a page comes back empty; the agent and research read the lookback alone, but for a script that names a first day on daily or longer bars, which is read from that day on through the same cache.
- `live-stream` holds the provider's one stream, which the `live-candles` and `live-depth` hubs share since a plan may allow a single connection, and a restart has each watch its listings again on the next one. The `live-depth` hub keeps the depth of each listing a window follows, one watch per listing however many windows follow it: on the stream where it takes the listing, a subscription beside its bars, and otherwise read every five seconds through its market's regular session and once as it ends, since a book changes only then. Depth replays nothing as it is subscribed, so a watch starts from a read. Only a listing's page follows its depth, so the plan's subscriptions go to what the user is looking at.
- The user's trading mandate is sealed in the secret store under its own key, never the config file, so no edit of the app's files makes or widens one, and the settings module holds it decrypted for the desk to read at every proposal. Only the settings page's procedures set or revoke it, binding it to the account the desk trades now and dating it from the days the user gave; the agent reads it through `get_setup` and changes nothing. An order sent under it that went unanswered, or that the app's exit cut off, sets `trading.locked`. Like every secret, it stays out of backups.
- The order desk trades the broker `trading.broker` names and, at Fubon, the stock account `trading.account` names, which the user picks among those the sign-in lists, so the app never guesses which account orders go to; Fubon with none picked trades nothing. Both are read once as the app starts, so a switch waits for a restart and the desk dismisses what waited for the other account as it opens. With Fubon it reads the account through the market module's one Fubon session, which then stays signed in while Taiwan's charts come from another source. That sign-in is set up in the Brokers section, apart from Taiwan's source, so one the user asks for stays while charts come from elsewhere and its accounts can be picked; charts leaving Fubon sign it out unless the desk trades through it.
- The exit watch, a pass with the scheduler every minute while a market is in its regular session, has the desk ask the broker which exit legs it still watches, so one sale ends the rest; the paper account follows its exits' listings on the live stream's minute bars, which take symbols of the plan's stream as charts do, and checks the last price of a listing the stream does not cover only when asked. Only the user cancels an exit, through the proposals module.
- Fubon's SDK runs only in a utility process of its own, one per sign-in: its calls block until Fubon answers, its native code could crash, and it logs the ID number and account details to `./log` with no setting for it, so that process works from a folder in `userData`. Only the main process can start a utility process, so it starts that one when the backend asks and hands the backend its port, and tells it when the process ends. The backend calls it over oRPC on that port, sending it the decrypted credentials, ends it when Fubon does not answer in time, signs in once per saved settings on first use, and keeps a failed sign-in instead of retrying until the settings change or the user asks, since repeated failures could lock the account. The process streams Fubon's reports of the account's orders being placed, changed or filled over the same port, and while the desk trades Fubon each burst of them has the desk show the account anew and look for its unanswered orders.
- The market module's trading calendar reads each market's trading days once per exchange day from the provider that covers it, a year back on, and a market none covers trades every weekday; the agent's `get_news` counts sessions on it. The session a market is in is told on those days too, to windows, the agent and the order desk alike, through a reader that falls back to every weekday while the calendar cannot be read, so a provider out of reach never stops a session being told or an order being checked.
- The fundamentals module serves each market from the provider that covers it and keeps a listing's answer for half a day, since research asks for the newest quarter far more often than one comes out. A listing's restrictions, what it is as a fund, the multiples its exchange works out, the notices of its shares going ex and its shareholders' meetings come from the source of its exchanges' own lists instead, which answers for a whole market at once, so the module keeps a market's funds, meetings and companies, with the industry each is classed in and the shares it has issued, for half a day and the lists an exchange draws up each day for an hour, and every listing reads its own from them. A listing's standing among its industry's multiples is worked out from those two kept lists, so it costs no request of its own. A Taiwan sector's movers over the exchange's last session are worked out from the kept companies and that session's closes, so they cost no request of their own either. The order desk reads a listing's price limits through the module, and a list it cannot read leaves them unknown rather than failing the check. The paper account fills a market order at the listing's quote. A listed fund's net asset value and what it paid over a month come from the source of what funds report, which answers for a whole market at once too, so the module keeps a market's values for an hour, since one is struck after each session, and its costs for half a day. FinMind's token is the secret `finmind-token` and its plan `providers.finmind.plan`, which only sets how many requests an hour it allows. One FinMind client serves fundamentals, flows and the trading calendar, so all count against one limit. A window reads a listing's newest quarters and months through `financialTrends`, with growth worked out by the functions the agent's `get_fundamentals` uses, so what a window draws and what the agent cites agree.
- The flows module serves who trades each listing and market from the provider that covers it, a year back, each answer kept until FinMind has a session's next figures in (15:00, 18:00 and 21:00 Taipei), so a listing costs three requests at most that often and the market three. Nothing pushes, so the renderer lets them go stale on their own.
- A source reads over Node's `fetch` unless its server needs a browser's handling: the host's `chromiumFetch` reads over Chromium's network stack, which fetches an intermediate certificate a server leaves out of its chain. In the backend's process that is Electron's `net`, which sends and keeps no cookie and keeps no cached answer, so nothing a source sets is written to disk or shared with a window. Taiwan's statistics portal is read through it.
- The macro module keeps each market's schedule of economic releases, read from a week back so releases just out stay on it and twice a day at most, and its indicators' figures over the last twenty-six months, read once an hour at most, each from the source that covers the market. The calendar reads the schedule through it; the figures are read apart from the calendar, by windows through its `series` procedure and by the agent's `get_calendar` and `get_macro`, so a statistics database slow to answer never holds up the dates.
- The calendar module derives the coming events of the listings the renderer names from their fundamentals, read through the fundamentals module, so it costs no request beyond what that module keeps, a listing's filings and what its exchange lists of it each on their own so one source failing leaves the events of the other, and adds the dates their reports in force hold, read from the research database, and the closures and economic releases of their markets, a market's closures read twice a day at most and its schedule through the macro module. A release comes without its figures, which whoever shows it joins from the market's series, naming a market whose figures fail to read apart from one whose dates are missing. Nothing pushes when fundamentals or a schedule change, so the renderer lets those go stale on their own, and reads the calendar again whenever research changes. A listing or market that fails to read is named beside the others' dates, so a missing date is not taken for none.

## News and research

- The news module is the one `NewsDesk` the agent's `get_news` and `search_history` read through. It collects into `news.sqlite` on request and, for the listings the user holds or watches, as the plan `collection.news` has each due; a broker that cannot be read leaves the watchlist. The overview's headlines are ranked, and a listing's stories read for its symbol page, in the backend, so only the heaviest headlines and no item's vector cross IPC. Every search records its source's health: scheduled refreshes rest a source that keeps failing, while `get_news` always tries every source. Windows hear once per collection, and each story is scored once per listing by the decisions model the user set up.
- The web search module hands news and the agent the vendor `webSearch.provider` names, on the key saved under the vendor's id (`<vendor-id>-api-key`, the secret an agent provider of that id would use too), read afresh for every search. Until that key is saved, news searches only its keyless sources, the companies' material information, their insiders' declared transfers and PTT, and the agent gets no web tools.
- News groups by meaning only while `embeddings.enabled` is on, which it is not until the user switches it on. The embeddings module hands news the embedder `embeddings.provider` picks, read afresh for every collection and read: Ollama, on this computer unless the user names a host of their own, with the secret `ollama-embeddings-api-key` sent only where they saved one for a proxy, or OpenAI's on the secret `embeddings-api-key`, never the agent's or the decisions model's key. The settings name the host whenever Ollama's address leaves this computer, since everything below is sent there. While the embedder cannot be reached, items group by their titles alone. The module also tells windows whether Ollama holds the model its settings name, whichever provider is picked, and downloads it when the user asks: one pull per model at a time, kept in the backend so it goes on whatever the windows show, with how far it has come pushed at most twice a second and why it failed kept until the next pull. The user's own text, such as a report's falsifiers, what the agent searches for and its memories, is embedded only by Ollama, which the user runs, so with OpenAI's embeddings what reads it goes without vectors. After each collection, the research module has the desk read the listing's falsifiers against the week's news.
- The themes module holds the one `ThemeDesk` over the user's database and registers a pass with the scheduler that searches each theme's queries for news as the plan `collection.themes` has each due, through the web search vendor, on no market's calendar, one theme after another. Nothing is searched until that vendor's key is saved, a query that fails leaves the others' items, and a search that fails whole is tried again at the next pass. The agent's `search_theme` searches one theme through the call the themes tab's own button makes. It tells windows whenever a theme is written or removed and whenever a search finds or reads something.
- The agent's research tools check a new quote against what its conversation read, which the agent module hands them from the runtime's stored transcript, a compaction's hidden part among it.
- The decisions module hands research the claim auditor and the fact reader of the provider the user set up, read afresh each time, and neither until that provider's key is saved.
- The research module holds the one `ResearchDesk` over `research.sqlite`, which the agent's tools write through, and the renderer and the order desk, which keeps each proposal's basis, only read, and tells every window after each revision, reading of falsifiers against the news, forecast, settlement and clearing, and as an exchange's day turns or its regular session opens or closes, through a pass with the scheduler, since nothing else tells of either: the day turning passes a report's events, and a forecast settles when it is next read after its horizon's session closes, so the window reads it again then.

## Backups

- The backup module keeps backups in the bucket the user set up: its server, region, bucket and folder in the config file's `backup` section, and its access key and the passphrase as secrets. An object is `<folder>/<installation>/<moment>.solyx-backup`, the installation its UUID and the folder named after the app unless set, so each channel and each computer keeps its own and a listing tells them apart.
- `backup-places.ts` lists what a backup holds: every database but the cache, the config file, `mcp.json`, `AGENTS.md`, `skills/` and the conversations' folders. What is not listed there is not backed up, and the secret store never is, since the OS key that seals it stays on this computer. A link at one of those places is backed up as what it points to, so settings a person keeps elsewhere are in the backup too; a link inside a folder is left out.
- A backup is made while the app runs, from a snapshot of each database, and sealed before it is uploaded. A file or folder that changes as it is copied fails the backup, which names it, rather than go in by the part that was read. One backup or restore goes on at a time.
- The work of a backup and of a restore, everything that reads the databases, packs, seals and speaks to the bucket, is a job in `backup-jobs.ts` that a worker thread of its own runs and ends with, since packing and sealing would hold the event loop every window, the scheduler and the order desk share. The backend keeps what only it can do or must decide: the settings and the secrets, which it hands the thread decrypted, what is going on, when a backup is due and the swap as the app starts. A failure crosses back with its message and what kind it was, so the log names it as it would one of the backend's own.
- While `backup.automatic` is on, which it is once the destination is set up, the module's pass with the scheduler makes a backup each time `backup.every` has gone by since it last looked, and uploads nothing when what it would hold is what the last one held. It keeps when it last looked, what it last uploaded, where to and what the bucket held in `userData/backup.json`, which is no part of a backup. That is of one bucket and folder and of the passphrase then, so once either changes the next pass backs up whatever it would hold: another bucket holds none of the backups, and a new passphrase opens none. A backup that fails on its own is logged as recovered, shown on the backup tab and tried again a quarter of an hour after it failed, never every minute.
- After every backup that goes up, the module deletes the backups `@solyx/backup/retention` no longer keeps, reading days and weeks on the user's clock. It lists only this installation's folder and deletes only objects named as its own backups are, whatever else the server's listing names, so another computer's backups and anything else in the bucket are never touched, and one that cannot be deleted leaves the backup made.
- A restore changes nothing while the app runs, since the databases stay open until it quits: it downloads the backup, unpacks it under `userData/restore`, checks that every database is there, whole and no newer than this build, and restarts the app. `takeRestore` then puts the files in place at the top of `createServices`, before anything opens one, and moves what was there to `restore/previous`, where it stays until the next restore. A swap cut off partway goes on from where it stopped, and one that fails stops the app from starting rather than letting it start on half of each.
- The order desk is told when it opens on restored data and dismisses what waited in it, and the window opens on the backup settings, which say so.

## Scheduling, updates and telemetry

- Periodic work registers with the one scheduler in `scheduler.ts` as `ScheduledWork`, naming how long after a pass starts the next is due, and keeps no timers of its own. The clock starts once the services are built and stops as the app quits, skips a pass still going when its next is due, reports a pass that fails and leaves the others going, and ticks again as the computer wakes, since timers sleep with it. A pass decides for itself what is due within it, such as the news setting read before every pass.
- The schedules module sends the agent each scheduled task the user wrote once it is due, in a conversation of its own on the default model, with no listing on screen and the task's own language and clock. Its pass registers with the scheduler and starts due tasks one after another, and a slower pass of its own looks at the tasks that wait on a change, since telling what changed for the listings the user follows reads the account, which a live broker answers over the network; only a scope that names no listings of its own reads it. Such a run is told what changed within its scope and keeps it as its last run; a task whose last run is still going, as one waiting for the user is, is skipped rather than queued, and a run that could not start is kept as failed and not tried again before its next time. A run's approval mode is the task's, `ask` or `auto` and never `bypass`. The agent reads the tasks and writes one through the module's `save`, which the agent's tool guards, so a run nobody watches never keeps a task unasked; only the user removes one. It starts a task's run through `runNow`, the call the settings' button makes, which its tool guards the same way and refuses inside a run a task started. A task saved takes the user's clock and language as they are then, whoever saved it. It tells windows after every save, removal and run.
- What the app collects on its own, news for listings and news for themes, is timed by a `CollectionPlan` each in the config file's `collection` section: every so often or at a time of day that may keep to a market's trading days, never on a change, which is what collecting finds. Each module makes its own collection and decides per listing or theme what is due, so one the agent collected meanwhile is not collected again, and a time of day the app slept through is still made up for however late. The collections module only gathers the plans and each collector's status for the Schedules tab, beside the tasks the agent is sent; a collection is never a task, since it has no prompt, model or conversation.
- The updates module reads the feed of the channel the app was built for a minute after start and every six hours while `updates.check` is on, and whenever the user asks. Windows downloads the update and installs it on restart or quit; macOS installs only through Squirrel.Mac, which needs a Developer ID signature, so there the update links to its GitHub release. Development builds, the test package and Linux never check.
- Traces and logs go over OTLP/HTTP only to the endpoint the user sets in `otlp.endpoint`, with the headers saved as the secret `otlp-headers`, which must parse as `OTEL_EXPORTER_OTLP_HEADERS` writes them before they are saved, and nowhere while it is unset; the telemetry module follows both as they change. Neither of its providers is registered globally, so only what is handed its tracer is traced, each agent run and each scheduled pass, and only `diagnostics` logs, never a library's own instrumentation, which would record what a request carried.
- Every failure the backend does not rethrow goes through the telemetry module's `diagnostics`, never `console`, which lint allows only there and in command-line scripts. One the app recovers from, such as a provider that did not answer or a model on this computer that is not running, is `recovered`: logged. One nothing should cause is `report`ed: logged, and sent to Sentry once the user agrees to crash reports. A log names what failed as a dotted event, identifiers such as a listing, and the failure's type and HTTP status, never its message, which may echo part of a key; the terminal gets the whole of it. What a scheduled pass logs joins that pass's trace.
- Crash reports go to the project's Sentry only from a packaged build given a DSN, and only while `crashReports.send` is on, which it is not until the user switches it on in first-run setup or About; the agent cannot switch it. Sentry starts before the app is ready in every such build, so a report the user has not agreed to is dropped at its transport, queued ones included, and switching applies at once. The backend reports through Sentry's utility-process SDK, which hands each report to the main process, and the main process sends those and the renderer's too and scrubs every one: breadcrumbs beyond the app's lifecycle and processes ending, the renderer's address, a callback's arguments and the home folder go, and no minidump is sent, since it holds the process's memory.
