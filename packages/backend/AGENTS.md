# `@solyx/backend`

The app's backend, composed in `services.ts`. The desktop runs it in a utility process of its own, and it reaches Electron only through the `Host` port in `host.ts`. Rules that span it, the desktop's main process and the renderer, such as how windows reach the router, live in [`../../apps/desktop/AGENTS.md`](../../apps/desktop/AGENTS.md).

## Layout

- `modules/<module>/` holds a module's logic and its procedures in `<module>.route.ts`, built on `contractOS` from `rpc/context.ts`, or on `implement(<module>Contract)` over a context of only the services it reads where its tests need no more, as `settings` does. What only the process running the backend can do reaches a module through a small port, so it is tested without it.
- `scheduler.ts` is the one clock for periodic work.
- `host.ts` is everything the services ask of the process that runs them. Lint keeps `electron`, `electron-updater` and `@sentry/electron` out of every package, so the backend never depends on the process it runs in.
- `worker/<name>.ts` is a worker thread's entry, which the app running the backend builds as its own bundle, since a thread starts from a file.

## Settings and secrets

- `userData` holds secrets, caches and each database as its own file. Settings live in `~/.<app-name>/config.json`, JSON a person may edit; its `$schema` names the `config.schema.json` beside it, generated from the zod schema the app reads with and rewritten at start when it differs, so that schema, not comments, documents every entry. The backend watches the file and applies saved edits without a restart, keeps entries it does not read when saving, reads an entry that no longer parses as its default and replaces it when saving beneath it, and never overwrites a file with syntax errors.
- The config folder also holds what the user writes for the agent, read afresh for every run: `skills/`, `strategies/`, `AGENTS.md` and `mcp.json`, whose secrets are named `secret:NAME` and kept in the secret store. A skill shared through `~/.agents/skills` is offered only once it is listed in `agent.sharedSkills`.
- The config file and the secret store tell their listeners about every change, the app's own and a hand edit alike, so each module follows what it reads and a handler only saves.
- Secrets (provider keys, and the OAuth tokens of subscription, remote MCP and Longbridge sign-ins) are saved as ciphertext in `userData` with Electron's async `safeStorage`, reached through the main process, and decrypted only when a provider needs one; pi-ai and pi-mcp read and refresh them through a `CredentialStore` over the secret store. Where the OS has no secret store (Linux `basic_text`), nothing is saved.
- The renderer can save or delete a key and start, cancel or end a sign-in, but never reads a key back or sees a token.

## Devices and the edge

- The edge (`modules/devices/edge.ts`) is Hono on Node, listening on `127.0.0.1` at `remote.port` only while `remote.enabled` is on, and following both as they change. It answers only a request whose `Host` names this computer (`localhost`, `127.0.0.1`, `[::1]`, at any port, since `ssh -L` picks one), so a page that rebinds its own name to this computer reaches nothing, and takes a pairing or a socket only from a page it served itself (`Origin`).
- A pairing code lasts five minutes, works once and is gone after five wrong tries. The device's token is told only to that browser; the backend keeps its SHA-256, with the device's name, sealed in the secret store, so no edit of the app's files pairs one.
- A paired browser opens `/rpc` with its token beside the `solyx` subprotocol, since a browser sets no header on a WebSocket, and is served the router as `client` `{ kind: device }`. One that is not paired, or is unpaired while connected, is closed with `UNPAIRED_CLOSE_CODE`. Every procedure is refused to a device unless its contract marks it for devices, checked before its input is read, so a device never confirms, cancels at the broker, answers the agent's calls, unseals or changes settings.
- A browser adds a passkey only in the minutes after it pairs, so a token taken later adds none. The passkey is bound to `localhost`, since browsers bind none to an IP address, and sealed with the device in the secret store. To confirm, cancel an exit or cancel an order, a device asks `devices.actionOptions` for a challenge bound to that one action and target, good once for two minutes; the `…Signed` procedure checks the passkey's signature over it, user verified and from the page's own origin, before the desk is reached.
- How a conversation's calls are answered is set only from this computer's windows: a device starts only conversations that ask, and its messages and the runs it carries on ask every call that can ask, whatever mode the computer set. A proposal such a run makes still reaches the trading mandate as any agent proposal does.

## Agent

- MCP servers in `mcp.json` run as the backend's child processes or are reached over HTTP, and close when the app quits; `@solyx/agent` owns how they connect.
- The agent's models come from the providers switched on in `agent.providers`, plus the default model's provider, which is always on. An id the catalog no longer offers reads as switched off, and a default provider it no longer offers as the app's default one. `createAgentModels` reads and writes every setting that names a provider, and refuses an id the catalog does not offer before anything is saved for it. `agent.provider`, `agent.model` and `agent.thinking` are the default a conversation runs on until it picks its own. A provider runs only once its key (the secret `<provider-id>-api-key`) is saved or its subscription (`<provider-id>-sign-in`) is signed in, whichever `agent.auth` names, a key unless set otherwise; GitHub Copilot runs on its sign-in whatever `agent.auth` says, and OpenRouter's key may come from a sign-in, saved as the same secret. `agent.endpoints` sends a provider's requests to the user's endpoint on an API key only: a sign-in's tokens go to the provider's own endpoint and nowhere else.
- Ollama, a server the user runs, takes no key, and its secret is sent only where the user saved one for a proxy; it runs once it lists a model that can run the agent. It is asked for its models only once switched on, again whenever its endpoint or key changes and while its settings show, and windows are told only when the list changed. The last list is kept in `userData/agent-models.json`, restored before runs resume, and served from the endpoint set now.
- The agent reads the settings through `agent-setup.ts` as the settings page's readers give them, a secret only as its state, and changes only the settings `agent-setup.ts` lists, through the settings page's writers. A key, a sign-in, a provider switched on, an endpoint, the shell and its sandbox, MCP tool policies, shared skills, memory, the tray, where backups go, the account orders go to, the trading mandate and the lock on orders stay the user's alone, since each would widen what the agent reaches. It reads what each store holds through the storage module's `usage` and never clears one: clearing is the user's.
- The addresses the agent links to are built in `@solyx/api` beside the shapes the router reads them with, so a reply's link and the router cannot drift apart.
- `message-context.ts` names what the window showed as the agent's tools name it, so the context never carries the renderer's own ids.
- A message's `@` codes resolve against the listing on screen and the watchlist, then the account's holdings only for a code those miss, since a live broker answers over the network, then the listing search's exact codes in any market; its leading `/name` resolves against the offered skills the user may ask for. A token that names neither stays the user's text, and a source that fails leaves out only what it knew.
- The files a message carries are read again as they arrive, and only what the agent reads of each is kept, so backups hold nothing twice: an image only as its message carries it, scaled, and a text file and a PDF's text in a folder of the message's own under `attachments/` in its conversation's folder, which goes with the conversation; a message that is not sent takes its folder away again. Each image is scaled on Photon in a worker thread of its own, which ends with it or after a minute, so decoding never holds the event loop. Each PDF is read the same way, on unpdf's pdf.js with a cap on its heap and the CMaps shipped beside the bundle, which Chinese text in a font that names one needs; one locked with a password, or holding no text, keeps nothing of its message. A paired browser attaches files as a window does.
- A conversation's commands write in its folder, so `read_attachment` reads a kept file only at a kept file's place, never through a link a command left there, and attachments are written only as new files in a new folder whose real place is inside it. A conversation's id names its folder only as a single name, so no id reaches past `agent-workspaces`.
- The agent's shell is off until `agent.shell` is switched on, and stays off whatever that says while the desk trades a live account. Each conversation's commands work in its own folder under `userData/agent-workspaces`, erased with the conversation. `agent.shellSandbox`, on unless the user turns it off and read for every command, runs them in the sandbox on macOS and Linux; Windows has none. The services make the one sandbox, from which no command or strategy's code may read the home or the app's data and config folders, and hand it to the shell and the strategies; the shell may read the folders of the skills offered.
- One `MemoryStore` over `memory.sqlite` tells every window after each write, whoever wrote. Deleting a conversation keeps what it saved. The agent gets its memories while `agent.memory` is on, which it is until the user switches it off; switched off, they stay saved.
- `agent.decisionMode` says who judges the agent's forecasts and order proposals: the agent alone, or the MAGI, which votes an order up or down and votes on each of a forecast's scenarios. Each MAGI unit answers on the model `agent.magi` names for it, or else on the conversation's, and each turn's context tells the agent the mode.
- `agent.titleModel` names the model that writes conversations' names, read for every name; without one each conversation is named by its own model.
- Sign-in callbacks: Sign in with ChatGPT listens on port 1455, a remote MCP server's sign-in on the port its client registration redirects to, each taking any free port when that one is taken; OpenRouter's and Longbridge's sign-ins listen on any free port. A sign-in that runs on a code opens no listener: the settings module pushes the code to the windows.
- pi-durable's reports, such as a task that threw or a run the app's exit ended, are `report`ed as `agent.durable`, naming the task's kind and extension.
- Once the conversations' store fails, the agent module reports it, tells every window, and answers so to any window that asks later; a window then offers a restart, which quits as the app always does, so what is open closes first. Orders are not held up: the desk keeps its own database.

## Backtests

- The agent's backtests and the windows' run on one kernel in a utility process of its own, which the main process starts when the backend asks: on the first run and again once one has ended. It keeps nothing between calls, and a run it does not answer within the deadline ends it, failing every run still waiting.
- A window's backtest reads a listing's bars through the candle cache as the agent's do, so the two read the same bars. It reads only what the app keeps and changes only the workspace's own history of runs, so a paired device runs one too.
- The history keeps one row per request, so asking again only updates it, and the newest `BACKTEST_HISTORY`; it tells windows of every change. A kept request is read back through its schema, so one that no longer reads is left out rather than failing the list. Comparing kept runs runs them again over today's bars and keeps nothing, so runs made on different days read side by side. The agent's backtests are not kept: they live in its conversation.

## Strategies

- The strategies module reads `strategies/` in the config folder afresh every time, each strategy read whole into memory once, with a version that digests every file's path and contents but what tools keep beside code (`.git`, `__pycache__`). A run copies those bytes into a folder of its own and runs the copy, so what runs is what was allowed whatever the folder holds by then. A folder that holds a link, whose target could change while the version stays, or that passes `MAX_STRATEGY_FILES` or `MAX_STRATEGY_BYTES`, is a problem rather than a strategy, since data, environments and packages belong outside it, on the PATH.
- A version runs only once allowed: in the sandbox, whoever allowed it, the user, the decisions model for a conversation set to auto or a conversation set to bypass; outside it, only where it was allowed for there; outside it beside a live account, only where the user allowed it themselves (`approvalAllows`). Approvals are sealed in the secret store, like the mandate, so no edit of the app's files allows one, and a device lists strategies but never allows one.
- A run works in a folder of its own under `userData/strategy-runs`, erased once it ends, where its code reads its input and writes its lines (`SOLYX_STRATEGY_INPUT`, `SOLYX_STRATEGY_OUTPUT`). It gets the environment a shell command gets, and while `agent.shellSandbox` is on runs in the sandbox, where it reads and writes only its run's folder, which is also its HOME, reads its PATH's tools and reaches no network. One past `STRATEGY_TIMEOUT_MS` ends with everything it started, and one that writes more than `MAX_OUTPUT_BYTES` is refused.
- The module writes a strategy's files only through `save`. A change is drafted first and refused where the folder would not then read as a strategy or would pass the limits, or where the files have left the version its writer read, so it never writes over what that writer did not see; one that leaves the files as they are is not refused. Writing allows nothing: a version written runs only once allowed, and `reviewDraft` shows what a change would make of the files beside the newest version allowed, so whoever allows it reads all it would let run.
- `runtimes` asks each interpreter a strategy's code would find on its PATH for its version, as a sandboxed run would, each on its own, so one that does not answer counts as missing rather than holding up the rest.
- The agent's `strategy` skill rests on `scripts/eval-strategies.ts`, so run it again after changing that skill or `save_strategy`. What it writes holds market data, so it stays out of the repository.
- Only the user removes a strategy, from a window: `trash` moves its folder to the computer's trash through the host and takes back every version allowed, so one put back asks again before it runs. `reveal` shows the strategies folder or the folder of a strategy the module finds, never a path a name does not.
- Each version allowed has its files kept under `userData/strategy-versions` while an approval names it, so a window shows what changed since; what may run is the approvals' alone.
- The code gives only lines: the engine fills, prices and costs every trade. The agent reads, allows and runs strategies through `strategy-port.ts`. Where the look-ahead check finds the code read later bars, the lines come with the line and the time of the first bar it did, which a result shows as a warning.

## Windows and the tray

- While `tray.show` is on, the app stays open in the menu bar or system tray once its last window closes, so the clock's work goes on; off, it quits with its last window, except on macOS, where it stays in the Dock. `tray.hideDock` takes it out of the Dock only while no window is open and the icon is there to bring it back.
- The tray module decides what the icon and the Dock show through the `Host` port, and the main process draws them. Whatever tells the windows of a change to what the menu lists tells the tray, which then reads it all afresh. A row opens the window at its place through the workspace module and never confirms an order or answers an approval itself.
- The agent module knows which conversations have a call waiting from its runs' events alone, since a question lives only as long as its run.
- The inbox module reads what waits as the tray's menu reads it, and research's backlog through `ResearchDesk.backlog`. It keeps nothing of its own, since each item leaves once it is handled, and tells windows whenever a proposal, a waiting call, research or the watchlist changes.

## Markets and providers

- The watchlist module is the one writer of the listings the user watches, and tells every window after each change, whoever made it.
- What is read from a provider on demand and kept for a while goes through `keepFresh` from `@solyx/utils/fresh`, its answers kept in `cache.sqlite` under a scope of its own, so a restart within the freshness costs no request and readers during an ask share it. A market's whole list from the exchanges or the fund reports that fails to read again stands as last read (`keepOnFailure`), since the exchanges' CDN can answer a list in another format for hours. Such reads never move onto the scheduler: a prefetch spends a provider's limit with nobody looking.
- Market data providers enforce the limits of the user's plan, so the backend keeps one provider per credential and plan. The market module follows the settings and keys, reopens the stream when they change and tells windows to load and watch again. It keeps a listing's names for the session once a source finds them, since news groups stories by them on every read.
- A listing's quote reads the five-minute series through the candle cache, never the stream, so the stream's subscriptions are left to charts and books and a refresh costs one intraday request; the agent's `get_quotes` reads the same quote. A market's sectors cost a request per sector index or fund, Taiwan's since the basic plan has no market snapshot, so they refresh slower and only while shown; the US's are the Select Sector funds against SPY. The agent's `get_sectors` reads through the same call, kept a minute, so the map and a call share one read. The renderer refreshes quotes and sectors only through the market's regular session, and once more as its after-hours session opens.
- The rotations module reads over Fugle's 360-day ranges of daily bars through the candle cache, newest first, and streams the newest range's paths first, since the plan's history budget holds the older ones back a minute or more. The sector indices take their session from the heat map's kept quotes, so the sectors' graph spends one intraday request, the TAIEX's, beside the map's. Bars are kept in memory while the exchange's day and session are those they were read in, and five minutes at most through the regular session, so a change of benchmark and `get_rotation` cost no request between. A benchmark other than the market's index is refused with why unless it qualifies.
- The `live-candles` hub keeps each watched symbol's session of minute bars from a `MarketDataStream` and pushes whole bars, so the renderer only upserts them by time; a symbol a restarted stream refuses ends the watches that followed it. Each `market.liveCandles` stream is one watch, and a symbol stops being live once its last watch ends. Only today's session is pushed; closed sessions come from history through the candle cache.
- `live-stream` holds one stream over each market's source, which `live-candles` and `live-depth` share since a plan may allow a single connection, and a restart has each watch its listings again. Taiwan's settings and keys restart it, and so does a Longbridge sign-in that changes the client, never a refresh. `live-depth` keeps one watch per listing however many windows follow it: a subscription on the stream where it takes the listing, and otherwise a read every five seconds through the regular session and once as it ends. Depth replays nothing as it is subscribed, so a watch starts from a read. Only a listing's page follows its depth, so the plan's subscriptions go to what the user is looking at.
- The user's trading mandate is sealed in the secret store under its own key, never the config file, so no edit of the app's files makes or widens one, and the settings module holds it decrypted for the desk to read at every proposal. Only the settings page's procedures set or revoke it, binding it to the account the desk trades now and dating it from the days the user gave; the agent reads it through `get_setup` and changes nothing. An order sent under it that went unanswered, or that the app's exit cut off, sets `trading.locked`. Like every secret, it stays out of backups.
- The order desk trades the broker `trading.broker` names and, at Fubon, the stock account `trading.account` names, which the user picks among those the sign-in lists, so the app never guesses which account orders go to; Fubon with none picked trades nothing. Both are read once as the app starts, so a switch waits for a restart and the desk dismisses what waited for the other account as it opens. With Fubon the desk reads the account through the market module's one Fubon session, which stays signed in while Taiwan's charts come from another source. A Fubon sign-in the user asks for apart from Taiwan's source stays too, so its accounts can be picked; charts leaving Fubon sign it out unless the desk trades through it.
- The exit watch, a pass with the scheduler every minute while a market is in its regular session, has the desk ask the broker which exit legs it still watches, so one sale ends the rest; the paper account follows its exits' listings on the live stream's minute bars, and checks the last price of a listing the stream does not cover only when asked. Only the user cancels an exit, through the proposals module.
- Fubon's SDK logs the ID number and account details to `./log` with no setting for it, so its process works from a folder in `userData`. The backend calls it over oRPC, sending it the decrypted credentials, ends it when Fubon does not answer in time, signs in once per saved settings on first use, and keeps a failed sign-in instead of retrying until the settings change or the user asks, since repeated failures could lock the account. The process streams Fubon's reports of the account's orders, and while the desk trades Fubon each burst of them has the desk show the account anew and look for its unanswered orders.
- US listings' data comes from Longbridge on the user's sign-in, the secret `longbridge-sign-in`, which needs no securities account. Each sign-in registers a client of its own with Longbridge, and replacing or ending it deletes that client from the user's account. The access token is refreshed before it expires, one refresh at a time, since each spends the refresh token. Each request Longbridge refuses as too fast is logged as `longbridge.rate-limited`, and each quote-server packet left out is reported as `longbridge.unreadable`. The market module has the client close its connection when the sign-in's client changes, so a refresh keeps it and a new sign-in, maybe of another account, opens another.
- Listing search ranks every market's listings in one list. A US ticker Longbridge's list lacks, as one traded over the counter, is found when typed whole. A market whose listings cannot be read is named unread beside the other's matches, so a search says so rather than finding nothing; a US signed out is not unread, since the window says to sign in.
- The trading calendar reads each market's trading days once per exchange day from the provider that covers it now, and a market none covers trades every weekday. The session a market is in is told to windows, the agent and the order desk through a reader that falls back to every weekday while the calendar cannot be read, so a provider out of reach never stops a session being told or an order being checked.
- The fundamentals module serves each market from the provider that covers it, US listings from Longbridge, whose reads fail while signed out, and keeps a listing's answer for half a day. What comes from the exchanges' own lists answers for a whole market at once, so the module keeps those lists and every listing reads its own from them; an industry's multiples and a Taiwan sector's movers are worked out from them at no request of their own. The order desk reads a listing's price limits through the module, and a list it cannot read leaves them unknown rather than failing the check. FinMind's token is the secret `finmind-token` and `providers.finmind.plan` only sets how many requests an hour it allows. One FinMind client serves fundamentals, flows, the trading calendar and Taiwan's index on total return, so all count against one limit. `financialTrends` works out growth with the functions the agent's `get_fundamentals` uses, so what a window draws and what the agent cites agree.
- The flows module keeps each answer until FinMind has a session's next figures in (15:00, 18:00 and 21:00 Taipei), so a listing costs three requests a day at most and the market three. Nothing pushes, so the renderer lets them go stale on their own.
- A source reads over Node's `fetch` unless its server needs a browser's handling: the host's `chromiumFetch` reads over Chromium's network stack, which fetches an intermediate certificate a server leaves out of its chain. It is Electron's `net`, which sends and keeps no cookie and no cached answer, so nothing a source sets is written to disk or shared with a window. Taiwan's statistics portal is read through it.
- The macro module serves its schedules, figures, the US dollar's close in Taiwan dollars and US Treasury yields each as last read while its source fails, since each carries its day; the US's come from Longbridge and fail while signed out. The calendar reads the schedule through it, and the figures are read apart from the calendar, so a statistics database slow to answer never holds up the dates.
- The calendar module derives a listing's coming events from what the fundamentals module keeps, so it costs no request beyond it, with a listing's filings and what its exchange lists each read on their own, so one source failing leaves the other's events. A window reads each listing's events, the reports' dates and each market's releases and closures through procedures of their own, so a source slow or out of its limit holds up only what it serves. A listing or market that fails to read is named beside the others' dates, as is a market whose figures fail apart from one whose dates are missing, so a missing date is not taken for none. Nothing pushes when fundamentals or a schedule change, so the renderer lets those go stale, and reads the reports' dates again whenever research changes.

## News and research

- The news module is the one `NewsDesk` the agent's `get_news` and `search_history` read through. It collects into `news.sqlite` on request and, for the listings the user holds or watches, as `collection.news` has each due; a broker that cannot be read leaves out its holdings. Headlines are ranked, and a listing's stories read, in the backend, so only the heaviest headlines and no item's vector cross IPC. Every search records its source's health: scheduled refreshes rest a source that keeps failing, while `get_news` always tries every source. Windows hear once per collection, and each story is scored once per listing by the decisions model the user set up.
- The web search module hands news and the agent the vendor `webSearch.provider` names, on the secret `<vendor-id>-api-key` (the one an agent provider of that id would use too), read afresh for every search. Until that key is saved, news searches only its keyless sources and, while signed in to Longbridge, a US listing's filings, news and posts, and the agent gets no web tools. The web search finds Taiwan's articles alone, and both markets' social posts.
- News groups by meaning only while `embeddings.enabled` is on, which it is not until the user switches it on. The embedder `embeddings.provider` picks is read afresh for every collection and read: Ollama, on this computer unless the user names a host, with `ollama-embeddings-api-key` sent only where they saved one for a proxy, or OpenAI's on `embeddings-api-key`, never the agent's or the decisions model's key. The settings name the host whenever Ollama's address leaves this computer, since everything below is sent there. While the embedder cannot be reached, items group by their titles alone. The user's own text, such as a report's falsifiers, the agent's searches and its memories, is embedded only by Ollama, so with OpenAI's embeddings what reads it goes without vectors. A model download runs one pull per model at a time in the backend, so it goes on whatever the windows show.
- After each collection, the research module has the desk read the listing's falsifiers against the week's news.
- The themes module holds the one `ThemeDesk` and searches each theme's queries through the web search vendor as `collection.themes` has each due, one theme after another, on no market's calendar. Nothing is searched until that vendor's key is saved, a query that fails leaves the others' items, and a search that fails whole is tried again at the next pass. The agent's `search_theme` makes the call the themes tab's own button makes.
- The agent's research tools check a new quote against what its conversation read, from the runtime's stored transcript, a compaction's hidden part among it.
- The decisions module hands research the claim auditor and the fact reader of the provider the user set up, read afresh each time, and neither until that provider's key is saved.
- A report's stance is measured against its market's index on total return, kept twelve hours: Taiwan's from FinMind, since Fugle serves that index's session but not its history, and the US's as SPY's own bars carried over what it paid out, since no source serves the S&P 500's.
- The research module holds the one `ResearchDesk` over `research.sqlite`, which the agent's tools write through, and the renderer and the order desk, which keeps each proposal's basis, only read. It tells every window after each change and, through a pass with the scheduler, as an exchange's day turns or its regular session opens or closes, since nothing else tells of either: the day turning passes a report's events, and a forecast settles when it is next read after its horizon's session closes.

## Backups

- Backups go to the bucket the user set up in the config file's `backup` section, with its access key and the passphrase as secrets. An object is `<folder>/<installation>/<moment>.solyx-backup`, the installation its UUID and the folder named after the app unless set, so each channel and each computer keeps its own.
- `backup-places.ts` lists what a backup holds; what it does not list is not backed up, and the secret store never is, since the OS key that seals it stays on this computer. A link at one of those places is backed up as what it points to; a link inside a folder is left out.
- A backup is made while the app runs, from a snapshot of each database, and sealed before it is uploaded. A file or folder that changes as it is copied fails the backup, which names it, rather than go in by the part that was read. One backup or restore goes on at a time.
- Everything that reads the databases, packs, seals and speaks to the bucket runs as a job in `backup-jobs.ts` on a worker thread of its own, since packing and sealing would hold the event loop every window, the scheduler and the order desk share. The backend keeps the settings and secrets, which it hands the thread decrypted, when a backup is due and the swap as the app starts. A failure crosses back with its message and kind, so the log names it as one of the backend's own.
- While `backup.automatic` is on, which it is once the destination is set up, a pass makes a backup each time `backup.every` has gone by and uploads nothing when it would hold what the last one held. What it last uploaded is kept in `userData/backup.json`, which is no part of a backup, for one bucket, folder and passphrase, so once any changes the next pass backs up whatever it would hold. A backup that fails on its own is logged as recovered, shown on the backup tab and tried again a quarter of an hour later, never every minute.
- After every backup that goes up, the module deletes those `@solyx/backup/retention` no longer keeps, on the user's clock. It lists only this installation's folder and deletes only objects named as its own backups are, so another computer's backups and anything else in the bucket are never touched, and one that cannot be deleted leaves the backup made.
- A restore changes nothing while the app runs, since the databases stay open until it quits: it downloads the backup, unpacks it under `userData/restore`, checks that every database is there, whole and no newer than this build, and restarts the app. `takeRestore` then puts the files in place at the top of `createServices`, before anything opens one, and moves what was there to `restore/previous` until the next restore. A swap cut off partway goes on from where it stopped, and one that fails stops the app from starting rather than letting it start on half of each.
- The order desk is told when it opens on restored data and dismisses what waited in it.

## Scheduling, updates and telemetry

- Periodic work registers with the one scheduler as `ScheduledWork` and keeps no timers of its own. The clock starts once the services are built and stops as the app quits, skips a pass still going when its next is due, reports a pass that fails and leaves the others going, and ticks again as the computer wakes, since timers sleep with it. A pass decides for itself what is due within it.
- The schedules module sends the agent each scheduled task once it is due, in a conversation of its own on the default model, with no listing on screen and the task's own language and clock, one after another. Tasks that wait on a change are looked at by a slower pass, since telling what changed for the listings the user follows reads the account, which a live broker answers over the network. A task whose last run is still going is skipped rather than queued, and a run that could not start is kept as failed and not tried again before its next time. A run's approval mode is the task's, `ask` or `auto` and never `bypass`, and it takes at most the tool rounds the task sets. The agent writes a task only through the module's `save`, which its tool guards, so a run nobody watches never keeps a task unasked; only the user removes one. It starts a run through `runNow`, guarded the same way and refused inside a run a task started. A task saved takes the user's clock and language as they are then, whoever saved it.
- News for listings and for themes is collected on a `CollectionPlan` each in the config file's `collection` section, never on a change, which is what collecting finds. Each module decides per listing or theme what is due, so one the agent collected meanwhile is not collected again, and a time of day the app slept through is still made up for. A collection is never a task, since it has no prompt, model or conversation.
- The updates module reads its channel's feed a minute after start and every six hours while `updates.check` is on, and whenever the user asks. macOS installs only through Squirrel.Mac, which needs a Developer ID signature, so there the update links to its GitHub release. Development builds, the test package and Linux never check.
- Traces and logs go over OTLP/HTTP only to `otlp.endpoint`, with the headers as the secret `otlp-headers`, which must parse as `OTEL_EXPORTER_OTLP_HEADERS` writes them before they are saved, and nowhere while it is unset. Neither provider is registered globally, so only what is handed its tracer is traced, each agent run and each scheduled pass, and only `diagnostics` logs, never a library's own instrumentation, which would record what a request carried.
- Every failure the backend does not rethrow goes through the telemetry module's `diagnostics`, never `console`, which lint allows only there and in command-line scripts. One the app recovers from is `recovered`: logged. One nothing should cause is `report`ed: logged, and sent to Sentry once the user agrees to crash reports. A log names what failed as a dotted event, identifiers such as a listing, and the failure's type and HTTP status, never its message, which may echo part of a key; the terminal gets the whole of it. What a scheduled pass logs joins that pass's trace.
- Crash reports go to the project's Sentry only from a packaged build given a DSN, and only while `crashReports.send` is on, which it is not until the user switches it on; the agent cannot switch it. Sentry starts before the app is ready in every such build, so a report the user has not agreed to is dropped at its transport, queued ones included, and switching applies at once. The backend reports through Sentry's utility-process SDK, and the main process sends those and the renderer's and scrubs every one: breadcrumbs beyond the app's lifecycle and processes ending, the renderer's address, a callback's arguments and the home folder go, and no minidump is sent, since it holds the process's memory. Neither the main process nor the backend has Sentry add trace headers to the app's own requests, which would tell every provider and the user's servers the app's release and the project's key.
