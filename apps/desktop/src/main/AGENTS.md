# Main process

The app's backend, composed in `services.ts`. Layout, IPC, settings and secrets rules live in [`../../AGENTS.md`](../../AGENTS.md).

## Agent

- MCP servers in `mcp.json` run as the main process's child processes or are reached over HTTP, and close when the app quits; `@solyx/agent` owns how they connect.
- The agent's models come from the providers the user switched on in `agent.providers`, plus the default model's provider, which is always on. An id the catalog no longer offers reads as switched off, and a default provider it no longer offers as the app's default one; each provider's key is the secret `<provider-id>-api-key`. `createAgentModels` reads and writes every setting that names a provider, and refuses an id the catalog does not offer before anything is saved for it. `agent.provider`, `agent.model` and `agent.thinking` name the default a conversation runs on until it picks its own, and a provider's models run only once its key is saved or its subscription signed in. `agent.endpoints` sends a provider's requests to the endpoint the user set in place of its own, on an API key only: pi-ai tells a ChatGPT sign-in by OpenAI's own endpoint.
- The agent reads the settings through `agent-setup.ts` as the settings page's own readers give them, and a secret reaches it only as its state; the readiness checks it shares with first-run setup sit in `#shared/ipc/settings.ts`. It changes only the settings `agent-setup.ts` lists, through the writers the settings page uses: the appearance, Taiwan's source and the data plans, the default provider, model and thinking, the decision mode, news collection, the web search, decisions and embeddings providers and update checks. A key, a sign-in, a provider switched on, an endpoint, the shell, MCP tool policies, shared skills and memory stay the user's alone, since each would widen what the agent reaches.
- Before a message's context is written, the agent module resolves its `@` codes against the listing on screen and the watchlist, reading the account's holdings only for a code those miss, since a live broker answers over the network, and its leading `/name` against the offered skills the user may ask for. A token that names neither stays the user's text, and a source that fails leaves out only what it knew.
- The agent's shell is off until `agent.shell` is switched on, and stays off whatever that says while the desk trades a live account. Each conversation's commands work in its own folder under `userData/agent-workspaces`, erased with the conversation.
- The memory module shares one `MemoryStore` over `memory.sqlite`, which tells every window after each write, whether the agent's, the settings page's or clearing them all. Deleting a conversation keeps what it saved, since the user allowed each memory on its own. The agent gets its memories from its next run on while `agent.memory` is on, which it is until the user switches it off; switched off, they stay saved.
- `agent.decisionMode` says who decides the agent's forecasts and order proposals: the agent alone, or the MAGI. Under the MAGI each unit answers on the model `agent.magi` names for it, or else on the model of the conversation that put the motion, and each turn's context tells the agent the mode.
- Sign-in callbacks: Sign in with ChatGPT listens on port 1455, a remote MCP server's sign-in on the port its client registration redirects to, and each takes any free port when that one is taken.

## Markets and providers

- What is read from a provider on demand and kept for a while, such as a market's trading days and schedule of economic releases and a listing's fundamentals, goes through `keepFresh` from `@solyx/utils/fresh`, its freshness beside the call and its answers kept in `cache.sqlite` under a scope of its own, so a restart within the freshness costs no request, and readers that come during an ask share it. Such reads never move onto the scheduler: a prefetch spends a provider's limit with nobody looking.
- Market data providers enforce the limits of the user's plan, so the main process keeps one provider per credential and plan. The config file picks each market's source; the market module follows the settings and keys, reopens the stream when they change and tells windows to load and watch again. It keeps a listing's names for the session once a source finds them, since news groups stories by them on every read.
- A listing's quote reads the five-minute series a chart of that interval reads, through the candle cache and never the stream, so the symbols pane and the overview's heat map leave stream slots to charts and cost one intraday request per refresh. Taiwan's sectors cost a request per sector index, since the basic plan has no market snapshot, so they refresh at a slower pace and only while shown. The renderer refreshes quotes and sectors only through the market's regular session, and once more as its after-hours session opens.
- The `live-candles` hub keeps each watched symbol's session of minute bars from a `MarketDataStream`, folds them into the intervals windows watch and pushes whole bars, so the renderer only upserts them by time. Only today's session is pushed; closed sessions come from history through the candle cache. A chart starts from its interval's lookback window and, as it is scrolled to its oldest bar, reads the page of history before it, until a page comes back empty; the agent and research read the lookback alone.
- Fubon's SDK runs only in a utility process of its own, one per sign-in: its calls block until Fubon answers, its native code could crash, and it logs the ID number and account details to `./log` with no setting for it, so that process works from a folder in `userData`. The main process sends it the decrypted credentials over its message port, ends it when Fubon does not answer in time, signs in once per saved settings on first use, and keeps a failed sign-in instead of retrying until the settings change or the user asks, since repeated failures could lock the account.
- The market module's trading calendar reads each market's trading days once per exchange day from the provider that covers it, a year back on, and a market none covers trades every weekday; the agent's `get_news` counts sessions on it.
- The fundamentals module serves each market from the provider that covers it and keeps a listing's answer for half a day, since research asks for the newest quarter far more often than one comes out. FinMind's token is the secret `finmind-token` and its plan `providers.finmind.plan`; a change to either drops what the module keeps, so the restrictions a paid plan adds are read again at once. One FinMind client serves fundamentals, flows and the trading calendar, so all count against one limit.
- The flows module serves who trades each listing and market from the provider that covers it, a year back, each answer kept until FinMind has a session's next figures in (15:00, 18:00 and 21:00 Taipei), so a listing costs three requests at most that often and the market three. Nothing pushes, so the renderer lets them go stale on their own.
- The calendar module derives the coming events of the listings the renderer names from their fundamentals, read through the fundamentals module, so it costs no request beyond what that module keeps, and adds the dates their reports in force hold, read from the research database, and the economic releases of their markets, each market's schedule read twice a day at most. Nothing pushes when fundamentals or a schedule change, so the renderer lets those go stale on their own, and reads the calendar again whenever research changes. A listing or market that fails to read is named beside the others' dates, so a missing date is not taken for none.

## News and research

- The news module is the one `NewsDesk` the agent's `get_news` and `search_history` read through. It collects into `news.sqlite` on request and, for the listings the user holds or watches, every `news.collectEveryHours` hours (0 turns it off); a broker that cannot be read leaves the watchlist. The overview's headlines are ranked, and a listing's stories read for its symbol page, in the main process, so only the heaviest headlines and no item's vector cross IPC. Every search records its source's health: scheduled refreshes rest a source that keeps failing, while `get_news` always tries every source. Windows hear once per collection, and each story is scored once per listing by the decisions model the user set up.
- The web search module hands news and the agent the vendor `webSearch.provider` names, on the key saved under the vendor's id (`<vendor-id>-api-key`, the secret an agent provider of that id would use too), read afresh for every search. Until that key is saved, news searches only its keyless sources and the agent gets no web tools.
- News groups by meaning only while `embeddings.enabled` is on, which it is not until the user switches it on. The embeddings module hands news the embedder `embeddings.provider` picks, read afresh for every collection and read: a model on this computer through Ollama, which sends nothing off it, or OpenAI's on the secret `embeddings-api-key`, never the agent's or the decisions model's key. While the embedder cannot be reached, items group by their titles alone. The user's own text, such as a report's falsifiers, what the agent searches for and its memories, is embedded only by a model on this computer, so with OpenAI's embeddings what reads it goes without vectors. After each collection, the research module has the desk read the listing's falsifiers against the week's news.
- The research module holds the one `ResearchDesk` over `research.sqlite`, which the agent's tools write through and the renderer only reads, and tells every window after each revision, forecast, settlement and clearing. A forecast settles when it is next read after its horizon's session closes, so the renderer lets what it read go stale on its own.

## Scheduling, updates and telemetry

- Periodic work registers with the one scheduler in `main/scheduler.ts` as `ScheduledWork`, naming how long after a pass starts the next is due, and keeps no timers of its own. The clock starts once the services are built and stops as the app quits, skips a pass still going when its next is due, reports a pass that fails and leaves the others going, and ticks again as the computer wakes, since timers sleep with it. A pass decides for itself what is due within it, such as the news setting read before every pass.
- The updates module reads the feed of the channel the app was built for a minute after start and every six hours while `updates.check` is on, and whenever the user asks. Windows downloads the update and installs it on restart or quit; macOS installs only through Squirrel.Mac, which needs a Developer ID signature, so there the update links to its GitHub release. Development builds and Linux never check.
- Traces and logs go over OTLP/HTTP only to the endpoint the user sets in `otlp.endpoint`, with the headers saved as the secret `otlp-headers`, which must parse as `OTEL_EXPORTER_OTLP_HEADERS` writes them before they are saved, and nowhere while it is unset; the telemetry module follows both as they change. Neither of its providers is registered globally, so only what is handed its tracer is traced, each agent run and each scheduled pass, and only `diagnostics` logs, never a library's own instrumentation, which would record what a request carried.
- Every failure the main process does not rethrow goes through the telemetry module's `diagnostics`, never `console`, which lint allows only there and in command-line scripts. One the app recovers from, such as a provider that did not answer or a model on this computer that is not running, is `recovered`: logged. One nothing should cause is `report`ed: logged, and sent to Sentry once the user agrees to crash reports. A log names what failed as a dotted event, identifiers such as a listing, and the failure's type and HTTP status, never its message, which may echo part of a key; the terminal gets the whole of it. What a scheduled pass logs joins that pass's trace.
- Crash reports go to the project's Sentry only from a packaged build given a DSN, and only while `crashReports.send` is on, which it is not until the user switches it on in first-run setup or About; the agent cannot switch it. Sentry starts before the app is ready in every such build, so a report the user has not agreed to is dropped at its transport, queued ones included, and switching applies at once. The main process sends the renderer's reports too and scrubs every one: breadcrumbs beyond the app's lifecycle and processes ending, the renderer's address, a callback's arguments and the home folder go, and no minidump is sent, since it holds the process's memory.
