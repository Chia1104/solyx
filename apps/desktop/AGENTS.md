# `@solyx/desktop`

The Electron app: the backend runs in a utility process that the main process starts, the main process does what only it can and draws the windows and the tray, the preload bridges a window to the backend, other utility processes isolate native SDKs, and the renderer draws the workspace. Backend rules live in [`packages/backend/AGENTS.md`](../../packages/backend/AGENTS.md), main process rules in [`src/main/AGENTS.md`](src/main/AGENTS.md) and renderer rules in [`src/renderer/AGENTS.md`](src/renderer/AGENTS.md).

## Layout

`src` splits by process first, so each tsconfig keeps Node and DOM apart, then by module (`account`, `market`, `proposals`, `settings`, …). A module keeps one name across every process and package.

- Each module's oRPC contract and what the backend and the renderer both read of it live in `@solyx/api` ([`packages/api/AGENTS.md`](../../packages/api/AGENTS.md)), and the backend in `@solyx/backend` ([`packages/backend/AGENTS.md`](../../packages/backend/AGENTS.md)).
- `main/index.ts`, `main/shell/`: Electron's entry and what it drives: the backend's process, the windows, the tray's icon, dialogs, the cipher, the update feed and crash reports.
- `preload/index.ts`: forwards the port a window posts to the main process, which hands it to the backend, and carries Sentry's bridge; it exposes nothing to the page.
- `utility/<name>.ts`: a utility process's entry, beside `<name>.contract.ts`, the oRPC contract it serves on the port the main process hands it as it starts. The backend runs in one, `utility/backend.ts`, where `utility/backend-host.ts` implements its `Host`, asking the main process over `utility/host.contract.ts` for what only it can do. Native SDKs that block or could crash run only in one of their own.
- `renderer/modules/<module>/`: the module's TanStack Query options, built from `orpc.<module>.<procedure>` and keyed by `orpc.<module>.key()`, components, form schemas and hooks.
- `renderer/pages/`: route components that only compose modules.
- `renderer/components/`: module-neutral components composed from HeroUI, such as the error boundary fallback, the loading and error states every module renders, and the pane splitter, sheet, sections and symbol rows the workspace shares.
- `renderer/app/`: router, root layout, i18n, query client, theme and zod setup, and `rpc.ts`, the window's channel to the backend with its `client` and `orpc`, the client's TanStack Query utilities.

## Build and release

- Main, preload, utility processes and the backend's worker threads, from `@solyx/backend/worker/*`, are bundled with `vp pack`, which inlines `@solyx/*`, so what a bundle reads at runtime is copied beside it: beside the backend's, in `dist/utility`, each database's migrations for drizzle's migrator and QuickJS's wasm for the agent's scripts; beside the main process's, the app icon `resources/icon.png` and the tray's `trayTemplate` images, exported from `resources/tray.svg` in black on clear for macOS to tint. The renderer is built with `vp build`. The package workflow builds in the `release` environment, whose `SENTRY_DSN` the main bundle keeps and whose `SENTRY_AUTH_TOKEN` uploads the renderer's hidden source maps to Sentry; they are deleted before packaging, so none ship.
- `vp run package` packs those builds with electron-builder, configured in `build/`, into `release/`; they bundle every dependency but Electron, so the app ships no `node_modules`. The icon's source is `resources/icon.icon`, an Icon Composer document, so packaging for macOS needs Xcode 26 or later; `icon.png` and `icon.ico` are exported from its dark rendition, and the nightly icons differ only in their amber ink.
- A nightly is published on a schedule, at most one every six hours, from the newest commit on `develop` that passed CI, and only when that commit is ahead of the last nightly's. It is built from `build/electron-builder.nightly.yml` as Solyx Nightly, so it keeps its own data beside the stable app. A stable release is dispatched by hand and promotes the latest nightly's commit, so it only ships what nightly already ran; it then commits the version to `develop` and moves `main` to that commit. Versions are written into the build, and this package's `version` names the latest stable release. Each channel's update feed is uploaded after its installers, so it never names one not yet there.
- Until there are paid certificates the macOS app is ad-hoc signed and the Windows installer unsigned.
- A packaged app's fuses turn off `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and the inspector, and load app code only from the `app.asar` whose hash the binary carries, since its binary unseals every secret; Node work off the main thread runs in a utility process or a worker thread, never in a copy of Electron run as Node. The macOS app runs under the hardened runtime with `build/entitlements.mac.plist`, which allows V8's JIT and turns off library validation, since an ad-hoc signature has no team ID and the broker SDK is signed by its vendor.
- Only a development run and the test package accept remote debugging. `vp run package:test` packs an unpublished, unpacked Solyx Test from `build/electron-builder.test.yml`, with the stable app's fuses and hardened runtime but its own name, so its data and secrets are its own, and no update feed; smoke runs that drive the built app over the DevTools protocol use it. A stable or nightly build quits before it opens anything when started with `--remote-debugging-port` or `--remote-debugging-pipe`, since the protocol drives a window that can confirm orders. A packaged build's version names its channel (`-nightly.`, `-test`), so the channel is fixed in the `app.asar` the fuses validate and no flag or variable changes it at launch. The release and nightly workflows never build the test package.

## IPC

- Adding or changing a procedure touches its contract, its route and its renderer call site together.
- Each window posts one end of a `MessageChannel`, which the preload forwards on `RPC_CONNECT` and the main process hands to the backend, which serves the router on it with the services and the asking window as context, the window as `client` by its page's `webContents` id. oRPC is served over those ports alone, never over HTTP, and nothing makes a client of the router, so nothing but a window reaches `proposals.confirm`.
- A failure reaches the window with the backend's own message, which the renderer shows: the server turns any error that is not an `ORPCError` into one that keeps it, and input that does not parse into its issues in words.
- A module tells the windows that what it holds changed, whoever changed it (settings and secrets, market data sources, proposals, news), by publishing on the services' `windowEvents`; its `changes` procedure streams each to every window that follows it, until that window's port closes. A payload is an object, `{}` for a change that says nothing more. A stream whose every event matters, as the agent's runs do, keeps all it has not sent yet rather than the publisher's last hundred. The renderer refetches on a change rather than guessing what a mutation reached; a query goes stale on its own only for what nothing pushes.
- The preload never exposes `ipcRenderer` or a port to the page. Its Sentry bridge hands the renderer's crash reports to the main process.
- A module may use another module's query keys to invalidate what it changes (a confirmed order refreshes `account`); anything shared more widely moves to a package.
- The backend asks for a place in the window, such as the one a row of the tray's menu names, through the workspace module: it keeps the destination and pushes that one waits, and a window takes it on the push and again as it loads, so a window opened for it shows it too.

## Identity

- The app's name selects its `userData`, its config folder, `~/.<app-name>` (`~/.solyx`, `~/.solyx-dev`, …), and its OS secret store entry. Unpackaged runs rename it to `<productName> Dev`, so development never touches an installed build's data or credentials; packaged channels are separated by the product name they are built with.

## Appearance

- The appearance is a setting. The backend has the main process apply its theme through `nativeTheme.themeSource`, which the renderer's `prefers-color-scheme` follows, and pushes every change to the renderers, so the renderer never picks a scheme or price colours on its own.
- The language and the user's time zone are part of the appearance, since the backend writes in them too, as the tray's menu is. `resolveLocale` and `resolveTimeZone` turn the saved preferences into a catalog and a zone in either process, each against its own reading of the computer's, and `@solyx/api/clock` formats the app's own times for both.
- Palettes are sRGB hex in `@solyx/api/palette`, since the chart canvas and Electron's window chrome accept nothing else. The user picks one per scheme, built in or their own from `appearance.palettes`, which sets colours over a built-in palette but never the price pair.
- The renderer writes the picked palettes as the CSS custom properties HeroUI reads before its first render; the charts and window chrome read them directly.
