# `@solyx/website`

The project's website: the landing page and the docs, on TanStack Start and Fumadocs, prerendered and deployed to Cloudflare Workers through Void.

## Boundaries

- Every page is prerendered: `vp build` writes each one into `dist/client`, so a route that needs a server per request does not belong here. A loader reads what it needs where it runs, in the browser on client-side navigation, never through a server function: the Worker answers no navigation, and the prerender runs on workerd, where `staticFunctionMiddleware` cannot write its results to files. Search downloads the index `/api/search` exports and runs in the browser.
- Void deploys the site: `voidPlugin()` builds it for the Workers runtime, Cloudflare serves the prerendered files, and the Worker answers only what no file matches. The Worker's settings, including its one domain `usesolyx.trade`, live in `void.config.ts`; `void.lock.json`, which pins the account and the Worker, is committed beside it.
- The site follows `develop`, not the latest release: every push to `develop` that changes what the site is built from deploys it (`.github/workflows/website.yml`). A page about a feature goes live when it merges, so it lands with that feature's code.
- The download page offers each channel's newest release, and the changelog lists every release's merged pull requests. Both read GitHub's releases once per build, into `virtual:latest-releases` and `virtual:release-notes` (`src/lib/releases.ts`), never from the browser, and Nightly and Release redeploy the site after they publish. The changelog reads the notes GitHub generates, so a pull request's Conventional Commits title is its entry, grouped by type. Installers link to their GitHub release, which keeps every version: `download.usesolyx.trade` keeps only the newest nightly, so a link there would break with the next one. The visitor's system is read only after hydration (`useVisitorPlatform`), so every prerendered page is the same for everyone.
- The crawler only follows links, so `vite.config.ts` lists every page in every locale for the prerender itself.
- Every page has a social card, drawn by the client build in Node with Fumadocs' Takumi template from the same page list, into `dist/client/og`; its `og:image` comes from `src/lib/social-card.ts`. Neither the Worker nor a prerendered route draws one: TanStack Start's prerender writes a response as text, which breaks an image, and drawing one would run past Workers Free's CPU time.
- Docs are MDX in `content/docs`, ordered by each folder's `meta.json`: `setup/` for the sources a user brings, the pages on using the app, `data/` for how the app computes what it shows, and `files` for where it keeps things. They describe what the app does today, taken from its code and the root README, and change with the code they describe; a `data/` page changes with the `@solyx/core` code whose formulas, windows and limits it states.
- Fumadocs' MDX components a page may use are the ones `src/components/mdx.tsx` registers. A list or table inside one is set off by blank lines from its tags, or the formatter reflows it into a paragraph. Formulas are KaTeX through `remark-math` and `rehype-katex`, between `$$` alone, since prose quotes prices such as NT$20; only docs pages load KaTeX's stylesheet. A screenshot is `<Screenshot file="…">`, the same name in every locale: a file under `content/docs/images`, or under `docs/` on `assets.usesolyx.trade`, an R2 bucket that holds what is too large for the repository. The repository's copy wins. A copy may carry the page's locale and a colour scheme as tags (`name.zh-TW.dark.png`), and the page shows the one that fits best, its language before its scheme; both schemes' shots are drawn and the stylesheet shows one, since a prerendered page cannot know the reader's. The build asks the asset host once which shots it holds, so a shot uploaded there shows from the next deploy; one the host gives no answer for is offered anyway, so the host's trouble never fails the build. A shot that fails to load in the browser gives way to the next that fits, and once none is left a pencilled frame holds its place.
- The terms of use and the privacy policy are MDX in `content/legal`, read through their own collection and served at `/terms` and `/privacy` in each locale; the app's About and first-run setup link to them. The privacy policy names every place the app sends data and what each receives, so it changes with any code that sends something new, and its date with it.
- The site sends nothing about its visitors: no analytics, fonts self-hosted through Fontsource, and the Shaders canvas runs with `disableTelemetry`.
- The site speaks the app's locales, `en-US` and `zh-TW` (`src/lib/i18n.ts`). English keeps the site's own paths, and every other locale is the first segment of the path (`/zh-TW/docs/...`), through TanStack Router's optional `{-$lang}` segment and Fumadocs' `hideLocale: "default-locale"`. `useLocale` reads the locale from the path, not a route's params, so an address no route matches still speaks its language. Each locale is prerendered on its own, so every page in every locale is listed in `vite.config.ts`.
- Copy lives in `@solyx/i18n`'s `website/` catalogs and reaches components through `react-i18next`, with one i18next instance per locale, so pages prerendered side by side never share a language. The demo workspace shows the app, so its labels come from the app's own `desktop/` catalogs. Its script returns data, not sentences, and the agent pane words it.
- A docs page in another locale is `name.<locale>.mdx` beside the English one, with its links written to its own locale's paths. Each of its headings ends with the English heading's id (`## 標題 [#english-id]`), so an anchor is the same in every locale and a link changes only its path. Search finds only pages in the language on screen.

## Theme and components

- `src/styles/app.css` sets the app's Blueprint palette as shadcn's tokens (`--background`, `--primary`, `--muted-foreground`, …). Fumadocs reads them through its `shadcn.css` preset, so the docs and the landing page share one theme. Tokens shadcn has no name for (`--graphite`, `--hatch`, `--stipple`, `--rise`, `--fall`, the candles, the ink's gradient ends) sit beside them.
- Interactive pieces are shadcn's Base UI components in `src/components/ui`, added with the shadcn CLI (`components.json`, style `base-vega`) and edited in place. Where no shadcn component fits, use the Base UI primitive directly, as the watchlist does with `ToggleGroup`. A link styled as a button stays a link and takes `buttonVariants`. A link in running text takes the `link` utility, which draws it as Fumadocs draws links in the docs; a list of navigation links takes Fumadocs' header style, muted until hovered.
- An address no route matches and a route that fails to load or draw both show a `StatusSheet`, through the router's `defaultNotFoundComponent` and `defaultErrorComponent`: the status drafted in pencil as isometric block letters, which the pointer inks, then the ways out. Retrying invalidates the router, which reloads the route and clears its error boundary.
- Motion uses the theme's `ease-out` and `ease-in-out`, which `app.css` redefines as strong curves. Reveals travel left to right, the way a pen moves. Under reduced motion, only fades remain. A loop runs only while its section is on screen (`useInView`). Under reduced motion, and before scripts run, it shows its finished state.

## Landing page

- It is drawn on the app's drafting sheet: hatching, stippling and dashed outlines are pencil, what the agent drafted, and the primary colour is ink, what the user signed.
- Below the hero, the page sits between the sheet's dashed rails (`Sheet`). Each band is ruled off by a `SheetRow`, with a registration mark where the rule meets a rail. Cells share hairlines instead of floating as cards, and only one is filled with ink. The site's own buttons are pills; the demo keeps the app's corners, since it shows the app.
- The hero panel's lower edge is the horizon. The sun is inked above it, with a halftone halo that grows as it rises, and pencilled below it. The pointer works as a pen, inking the dots it passes over. `--sun` on the page sizes both halves. The hero's copy overlaps the inked half and the demo's heading the pencilled one, each over a `scrim` of the surface beneath it so it stays legible. The inked half is drawn on a WebGPU canvas from `shaders`, which loads after the page since the engine carries every effect it offers. Where WebGPU is missing, an SVG draws it at rest. Canvases take the sheet's colours from the stylesheet through `useSheetColors`, so a theme change repaints them.
- The demo workspace runs on made-up prices from a fixed seed, so the server and the browser draw the same bars, and it fetches nothing. It reuses the app's own pieces where they are domain-free or pure: `@solyx/trading-chart` for the chart and `@solyx/core` for ticks, lots and indicators. Every price it shows sits on its listing's tick, and a proposal stays inside the next session's limits, as the app's risk checks would demand.
- The model providers the sources section lists, in `providers.tsx`, are the agent's catalog as the app offers it: pi-ai's built-in providers less those `@solyx/agent`'s `models.ts` withholds, one per company, plus Ollama. They change with that catalog, and the web search vendors beside them with `@solyx/web-search`'s. The logos are lobe-icons', as the app's own settings use.
- Confirming a proposal is the only button that fills with ink, as in the app, and only while it is held (`HoldButton`), so no `Button` takes the default variant.
