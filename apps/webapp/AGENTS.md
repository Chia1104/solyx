# `@solyx/webapp`

The workspace's React app, which each of the desktop's windows loads and the backend's edge serves to paired browsers. It reads everything from the backend through the oRPC client in `src/app/rpc.ts`: a window over the port its preload forwards, a paired browser over a WebSocket to the edge that served it. A window's crash reports reach the main process through the preload's Sentry bridge; a browser sends none. Paths below are under `src/`.

## Layout

- `modules/<module>/`: the module's TanStack Query options, built from `orpc.<module>.<procedure>` and keyed by `orpc.<module>.key()`, components, form schemas and hooks.
- `pages/`: route components that only compose modules.
- `components/`: module-neutral components composed from HeroUI, such as the error boundary fallback, the loading and error states every module renders, and the pane splitter, the page, its sections and the symbol rows the workspace shares.
- `app/`: router, root layout, i18n, query client, theme and zod setup, and `rpc.ts`, the window's channel to the backend with its `client` and `orpc`, the client's TanStack Query utilities.

## Build

- `vp run build` builds into `dist/` with relative paths, since the desktop loads it from `file://`, and a content security policy that only builds carry. The package workflow's `SENTRY_AUTH_TOKEN` uploads hidden source maps under the desktop's release, `solyx@<version>`, and deletes them. The desktop serves the dev server on the port `SOLYX_RENDERER_URL` names.

## Paired browsers

- `app/device.ts` tells a window, whose user agent names Electron, from a browser. A browser that holds no token shows only `pages/pairing-page.tsx` and loads nothing else, so it opens no socket until it pairs; its token lives in its own `localStorage`, and a socket closed as unpaired forgets it.
- A browser changes no settings, as the backend refuses those to devices anyway: it skips first-run setup, settings and their pane, the update action and the lock on orders, and shows answering the agent's call, and trying a parked run again, as left to the computer, since a run a window started may run calls unasked.
- Pairing at `localhost` offers to add a passkey, the only time the backend takes one. A browser that holds one submits a proposal and cancels an order or exit through the `…Signed` procedures, its passkey signing each action (`modules/devices/device-signing.ts`); one without shows them as left to the computer. It shows no approval mode, since a browser's messages ask before every call whatever the mode.
- A socket that closes for any other reason reloads the page after a few seconds, so the streams the page followed start again.

## Stack

- TanStack Router with hash history, since builds load from `file://`; TanStack Query for everything read from the backend; zustand for client-only state; TanStack Pacer's hooks for debouncing and throttling, such as a search that goes out once typing pauses, which cancel what is pending as their component unmounts.
- Back goes to the previous page, so a choice within a page, such as a chart's interval, the pane under it or a settings section, replaces its history entry rather than pushing one; first-run setup is a single entry, which leaving it replaces.
- A stream that only refreshes the query cache, such as a module's `changes`, is followed through `forEachEvent` by a `followXxx(queryClient)` beside the module's query options, called once in `main.tsx` for the window's whole life, so a query that never goes stale on its own hears of every change whichever page is open. What several places read and changes with the clock, such as sessions and quotes, refreshes there on one timer too, since every observer with a `refetchInterval` polls on its own and a listing shown twice would cost its provider twice. A component follows a stream only for state of its own, opened with a signal it aborts as it unmounts, as a chart follows its live candles and again when the sources change. The agent's events have one stream per window, which `followAgentEvents` folds, so what else hears of a run, such as the scheduled tasks, reads them there.
- HeroUI v3 on Tailwind CSS v4, used directly. Compose `react-aria-components` where HeroUI has no equivalent; add no other primitive library.
- A list with no limit, such as the conversations, a listing's news or the watchlist, is a react-aria collection (`ListBox` or `GridList`) under HeroUI's `Virtualizer`, which renders only the rows in view, inside a pane that scrolls too.
- A listing's price chart and the panes under it are Lightweight Charts through `@solyx/trading-chart`. Every other figure is drawn in SVG or HTML, and `d3-scale` and `d3-shape` compute any scale or path it needs. Each mark that names itself is a `ChartMark`: a focusable image whose HeroUI `Tooltip` says what it stands for, as the heat map's tiles do.
- The app's language and the user's time zone are part of the appearance: `app/i18n.ts` follows the language before the first render and on every push, and `app/clock.ts` reads the zone. The composer sends both with every message so the agent's context carries them, and with them what the window shows: the listing with its chart's interval and the indicators that chart draws, or the overview's tab and the market it keeps to, the settings' section or the strategies page and the strategy it shows. Detaching the listing from a message sends nothing of the screen. The times of the app's own events, such as messages and memories, are formatted through `useClock`, which renders its component again as the user's day turns, since a time of today is told without its date; anything on a market's calendar, such as charts, sessions and news, reads the exchange's zone from `@solyx/core/market` and never the user's.
- Forms use react-hook-form with `zodResolver`; each HeroUI field is wrapped in a `Controller`, and validation messages come from the catalog. A setting that takes one value is edited in its row; a longer form, and a setting's details, open over the page in `EditorModal` with their actions in `EditorFooter`, which a click beside it does not close.
- The composer suggests a listing after `@` and a command or skill after a leading `/` through react-aria's `Autocomplete` around its textarea; a command runs in the app rather than being sent. The list holds every candidate and the `Autocomplete` filters it, so focus never rests on an option filtered away. With no list open it handles no key, so Enter sends as before. Chromium fires `selectionchange` at the textarea without bubbling, so the caret is followed there rather than through `onSelect`.
- The composer carries the files the user picks with its + button, drops on it or pastes, each read by `@solyx/agent/attachment`'s rules as it is added, so a file the backend would refuse is refused there with why, and never sent. An image is held back while the conversation's model sees none, rather than sent for it to miss. A sent message shows its files above its text as their pictures alone, an image's as its message keeps it, scaled for the model, each naming itself in a tooltip. Pressing a file, there or in the composer, opens it over the page as the agent reads it: the image, or the text, a PDF's as read of it, cut to its first `PREVIEW_CHARACTERS`.
- The production CSP forbids eval and remote sources, so zod runs `jitless`; inline `<style>` and images from `blob:` URLs, which only the page mints, for the files a message carries, are the only relaxations.
- A place the backend asks for (`modules/workspace`) is a route, or the agent pane's tab and conversation, which the agent store holds so they can be shown from outside the pane.
- A link in an agent reply into the app (`#/…`), such as a settings tab `get_setup` names or a listing's page the prompt gives the address of, opens its page through the router; an https link opens in the browser only after the user reads its address, and any other is shown as text.
- An `html` fence in an agent reply is drawn as a canvas: a `srcdoc` frame sandboxed without scripts, under a policy of its own that refuses every request, and the main process stops any frame from navigating off its `srcdoc`. It is same-origin only so the renderer can size it and send its links through the agent's link dialog; it reads the app's colours as custom properties and nothing else of the app. Its stylesheet also carries the kit's marks (`agent-canvas.css`): bars, columns, shares, ranges and lines that size and place themselves from the figures a canvas gives as custom properties, so a reply states numbers and places nothing by hand. The `canvas` skill in `@solyx/agent` teaches those classes, and a test fails when the two part.
- The conversation shows each exchange (`threadTurns`) as the user's message, then what the agent worked through folded under one heading, then the calls that wait on the user or hold something for them (an approval, a proposal or vote, a forecast, a sector map, an analysis's backtests), which stay in view, then the answer: the last reply, once no call followed it, so a reply a later call followed joins the work. While the run goes, the heading names the step it is on (`currentStep`), a call waiting on the user before one being written or run, and once it is over, how many calls the agent made and how long it took. A call shows from when the model begins writing it, so a long one, such as a report, is seen being written rather than only once it has run.
- The agent pane's tabs are its header row: the conversation, with the controls over which one; what waits on the user or the broker (proposals, working orders, fills); the order panel; and what the account holds and has made. A proposal shows in the queue's own `ProposalItem` wherever it shows, the order panel's own under it included, so confirming is the same act everywhere. The order panel only proposes, through `proposals.propose`, and an edit dismisses the proposal it made while that one waits, since it no longer says what the user wants. On a listing's page it trades that listing; elsewhere it trades the one `useTicketStore` holds, which the last listing page set or the user typed, and it opens only once the market's source lists that one. It stays mounted behind the pane's other tabs, so a draft outlives a look at them, and follows the book only while in view. A price picked from the book or a click on the chart while the panel asks for one reaches the panel through the same store and brings the tab into view; so does a sale asked for from a holding, once it has opened that listing's page, so a sale is never written beside another listing's page. Neither sends anything, so the user still checks and confirms. The symbol page shows only its listing's side of the account: what is held of it beside the book, and its working orders and fills under the chart. The chart draws what the account does in the listing in the workspace's pencil and ink: what is real (the average cost, working orders, watched exits, fills) in ink and a proposal still waiting in pencil.
- The symbol page charts bars of the interval picked or, as `chart=session`, the newest session on minute bars against its reference price, the price scale even about it and the axis held open to the session's close; the agent is told that view as minute bars with their VWAP.
- Routes fall back, under a header of their own, to `ErrorFallback` through the router's `defaultErrorComponent`, which reports the error, since a boundary keeps it from reaching Sentry. A widget that can fail on its own, such as the chart, sits in TanStack Router's `CatchBoundary` so the rest of its page stays usable.
- A listing's backtest panel runs backtests through the backend and never the agent, so it spends no model's tokens: a template with its numbers, written rules or a strategy the user wrote with the numbers its code takes, over the listing's last years. A strategy runs only once its version is allowed, which a window does after the panel shows what changed since the version allowed before, and a browser leaves to the computer; where its code read later bars, saying so leads the run's warnings, since every figure then rests on prices it could not have known. The agent's call to allow one shows the same changes on its card, and its call to save one what the save would make of the files beside the newest version allowed, since allowing the save allows that version. The run it shows is kept per listing for the window's life, and while the chart above shows that run's interval it marks the run's trades in pencil, since none of them traded. What keeps a run from saying much (a stretch under twenty trades, out-of-sample timing no better than chance, an out-of-sample record behind holding) leads its figures, as the agent's backtest skill weighs them. Rolling windows lead with the share of starts that beat holding beside how many windows fit end to end, since windows that overlap say less than their count. A scan's heat map shows each cell's in-sample Sharpe ratio alone, and the out-of-sample figures only of the cell picked and only once asked for, so a grid is picked from on its in-sample stretch; a cell then runs alone as a single backtest. The panel's history lists the runs windows asked for, opens one in its mode again and compares up to four single runs, run again side by side over today's bars; it reads the history again as windows are told it changed, never the runs' own answers, which would run them again. The single run the panel shows rides with a message's screen while the panel shows it, so the agent runs it as the panel did, and buttons draft a request to read it or, for a template or rules, to keep it as one of the user's strategies, as the panel drafts one to write a strategy while the user has none; a script's single backtests open in the panel from the thread, their span and split the nearest the panel offers.
- The strategies page (`/strategies`), which the symbols pane opens, and each strategy's (`/strategies/$name`) are where the user's strategies are kept up: whether each may run and why not, its files, the versions allowed, the runs the backtest panel kept of it on every listing, and the folders that do not read as one. Running one on a listing opens that listing's backtest panel with it, so a strategy is backtested in one place. A paired browser reads them and runs backtests; allowing, taking back, showing a folder and moving one to the trash stay with this computer's windows, as does what a strategy's code runs on, whose read starts every interpreter on the PATH. Writing, changing and trading on one are drafted as requests to the agent, which the user sends.
- The research panel draws its own figures, from what the app keeps of a listing, the quote its page already reads and the listing's filings, which the fundamentals module is asked for only while the panel shows, so opening a listing's page spends none of that source's limit. It also places the listing on the rotation graph against its market's index and its own sector's, read through the backend as the overview's graphs are. A report's text is shown as plain text and never drawn as markup: a claim is checked against its quote, and a figure the agent drew into a report would pass no such check.

## Design

- The workspace is drawn in pencil and ink: hatching and dashed rules mark what is not real (paper trading, proposals awaiting confirmation), and the accent marks what is. Confirming a proposal is the only button that fills with ink, and only while it is held (`HoldButton`): letting go before it fills sends nothing, and only letting go ends a hold, since the page may reflow under a pointer that never moved.
- The window is the table, in the palette's background, which the window paints too, ruled into columns: the symbols pane, the routed page and the agent pane, with a hairline between each. There is no title bar: every column opens with its header (`ColumnHeader`), and together they make the window's top row, which moves the window and carries the band that says whether orders are paper or real (`broker-rule`). The pane toggles and back stay at the window's top corners whichever columns show (`WindowControls`), and the columns at the window's ends keep their headers clear of them and of the window's own controls (`--chrome-start`, `--chrome-end`). The symbols pane opens with the search and the pages it leads to, and its foot holds what stands wherever the user is: each market's session, paper or real, the lock on orders and settings.
- What a column shows lies on sheets (`sheet`), flat, without a shadow. One gap (8px) parts sheets from each other and from the column's rules and the window's edge. Text sits 16px inside what holds it, a sheet or a row, and the main view's header insets its text as far as its sheets' text sits. What is open in a pane, such as the listing on screen or the settings' section, lies on a sheet of its own.
- Inside a pane or a sheet, space parts rows and sections, never a rule. A row that takes focus fills a rounded inset while it holds it. A group that needs ground of its own, such as a list that scrolls apart from its sheet, a strategy or the holding beside the book, is set into its sheet as a `well`; one that stands for itself wherever it shows, such as a proposal, lies on a sheet of its own. The lines left each say something: pencil's dashes, a chart's axes and grid, and what HeroUI draws for its fields, tables and menus.
- A closed side pane shows over the main view, under the window's top row, on a floating sheet (`floating`, the only surface with a shadow, its rows the gap inside its edge) while the pointer rests on the window's edge beside it or on its toggle, and stays while the pointer, typing or keyboard focus is in it or in a menu it opened, since React passes their events to the pane. A press outside or an Escape nothing else took hides it, and its toggle or shortcut keeps it open. It is the pane's own content moved, so its scroll and drafts carry over, and only a mouse opens it.
- Routed pages respond to the `@container/main` width and the symbols pane's rows to `@container/symbols`, not the window's, since the panes are resized independently of it.
- Motion answers a user's action or marks what changed. What is done often or by keyboard snaps, such as moving between listings or a pane shortcut. Curves are HeroUI's tokens: `--ease-out-quint` to enter or leave, `--ease-in-out-quart` to move on screen. The step the agent is on shimmers while it goes and rises into place as the run moves on. Reduced motion drops movement but keeps fades and colour washes such as `highlight`.
- Red and green mark direction alone: a price's, or a released figure's from its previous period, so no gauge uses them. Which one marks a rise follows each market's convention (Taiwan the opposite of the US) unless the user picks one for every market.
- First-run setup is the `/onboarding` route, which takes the whole window until it is finished or skipped, and never shows once market data works. Each `OnboardingStep` reuses its feature's settings components, so setup a new feature needs becomes another step rather than a separate flow.
